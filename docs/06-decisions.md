### 만드는 순서와 날짜별 점검 지점

- **원칙(결정 26):** 만드는 순서는 빼는 순서의 거꾸로다. "빼지 않는 것"을 먼저 만들고, 빼는 순서 표의 아래쪽(21번)부터 위쪽(1번)으로 올라가며 만든다. 그래서 일정이 밀리면 아직 만들지 않은 위쪽 항목이 자연스럽게 빠진다.
- **점검 지점:** 그날까지 끝낼 것이 끝나지 않았으면 새 항목을 시작하지 않는다. 남은 날짜를 다시 세고, 표의 위쪽부터 뺀다.

## 결정 1. 송출 구조: LiveKit Cloud

- **결정:** 미디어 서버를 거치는 구조로 간다. 미디어 서버는 직접 운영하지 않고 관리형 서비스인 LiveKit Cloud를 쓴다.
- **결정일:** 2026-11-06

### 기기끼리 직접 연결하는 구조를 뺀 이유

- 방송자 브라우저가 시청자 한 명 한 명에게 영상을 따로 보내야 한다. 그래서 시청자가 늘면 방송자 쪽이 버티지 못한다.
- 녹화를 따로 만들어야 한다.
- 다른 네트워크에서 볼 수 있게 하는 중계 서버(TURN)를 직접 운영해야 한다.

### 비교한 후보

| | LiveKit Cloud | Cloudflare Stream (WebRTC) | AWS IVS 실시간 |
|---|---|---|---|
| 브라우저 송출 | 화면 공유, 탭 소리, 마이크, 카메라를 공식 SDK로 지원한다 | 브라우저에서 바로 송출할 수 있다(WHIP 방식) | 웹 SDK로 송출할 수 있다 |
| 다른 네트워크 시청 | 중계 서버가 기본으로 들어 있다 | 서버를 거쳐서 문제없다 | 서버를 거쳐서 문제없다 |
| 방송 끊김 감지 | 참가자가 나가거나 방이 끝나면 서버에 알림(웹훅)을 보낸다 | 연결과 끊김 알림이 있다고 알려져 있다. 확인 필요 | 이벤트 알림이 있다 |
| 녹화 | 녹화 기능(Egress)으로 파일을 저장한다. 파일 하나는 최대 3시간이다 | 브라우저 송출 영상의 녹화 지원을 확인하지 못했다. 공식 베타 문서에 "아직 지원하지 않음"이 있다 | S3에 저장한다. 참가자별 녹화는 추가 요금이 없다 |
| 비용 | 무료 플랜이 있다. 월 5,000 참가자·분, 동시 접속 100명, 녹화 월 60분이다(공식 가격 페이지) | 유료 플랜이 필요하다 | 무료 플랜이 없다. 참가자·시간당 과금이다 |

### LiveKit을 고른 이유

- **방송 상태 조건을 지키기 쉽다.** 탭을 닫거나, 공유를 멈추거나, 휴대폰이 잠기면 LiveKit이 서버에 알림을 보낸다. 서버는 알림을 받아 방송을 종료 상태로 바꾼다. 이 조건은 문제정의에서 핵심 문제와 함께 지키기로 했다.
- **다른 네트워크 시청 문제가 사라진다.** 심사자가 아이폰을 휴대폰 데이터로 써도 볼 수 있다.
- **녹화와 다시보기를 같은 서비스에서 해결한다.**
- **무료로 시작할 수 있다.**

### 위험과 확인할 것

| 위험 | 대응 |
|---|---|
| 무료 한도는 월 5,000 참가자·분이다. 무료 플랜은 한도를 넘으면 요금이 붙지 않고 새 연결이 실패한다(공식 문서). 방송자 1명과 시청자 2명이 30분 방송하면 90 참가자·분을 쓴다 | 개발 테스트는 짧게 한다. 심사 직전에 사용량을 확인한다. 유료 플랜은 쓰지 않는다(결정 6). 한도는 매달 1일에 초기화된다 |
| **무료 플랜의 녹화는 한 달에 60분뿐이다(공식 가격 페이지).** 화면 공유를 녹화하는 참가자 녹화도 이 60분에서 빠진다. 넘으면 새 녹화가 실패한다 | 개발 중 녹화 테스트는 1~2분으로 짧게 한다. 유료 플랜은 쓰지 않는다(결정 6) |

### 이 결정으로 풀리는 가정

[05 가정 우선순위](05-assumption-priorities.md)의 가정 11(다른 네트워크 시청), 12(끊김 감지), 14(녹화)는 LiveKit 기준으로 확인하면 된다. 실제 동작은 이번 주 확인 4번(휴대폰 데이터 시청 테스트)에서 본다.

## 결정 2. 배포 서비스: Vercel + Firebase + Cloudflare R2

- **결정일:** 2026-11-06
- **예상 비용:** 0원. 모두 무료 플랜으로 시작한다. LiveKit 무료 한도를 넘으면 LiveKit만 유료로 올린다.

| 역할 | 서비스 | 고른 이유 |
|---|---|---|
| 웹 서버 | Vercel | Next.js와 가장 잘 맞는다. HTTPS 주소가 자동으로 나와서 아이폰 카메라 조건을 채운다. 서버 함수가 최대 5분까지 실행되어 LiveKit과 결제 서비스의 알림을 받기에 충분하다 |
| 데이터베이스 | Firebase Firestore | 실시간 구독이 기본이라 새 댓글과 방송 상태가 시청 화면에 바로 반영된다. 무료 플랜도 프로젝트가 멈추지 않는다. (결정 12에서 채팅 전달은 LiveKit으로 바꿨다. Firestore는 채팅 저장과 방송 상태 구독에 쓴다) |
| 로그인 | Firebase Auth | 이메일 가입, 로그인, 로그아웃, 로그인 상태 유지가 들어 있다. 테스트 계정 바로 로그인 기능도 쉽게 붙인다 |
| 녹화 파일 저장소 | Cloudflare R2 | 무료 용량이 10GB다. 내려받기 전송 요금이 없어서 다시보기 재생 비용이 들지 않는다. LiveKit 녹화 기능이 S3 호환 저장소로 바로 올린다 |
| 미디어 서버 | LiveKit Cloud | 결정 1에서 정했다 |

### 지켜야 할 조건: 쓰기는 모두 서버를 거친다

공모 요강은 "서버에서 인증 상태와 방송 소유자 권한을 확인"하라고 요구한다. 브라우저가 Firestore에 바로 쓰면 권한 확인이 보안 규칙 안에 숨는다. 그러면 심사자가 서버에서 확인했다고 보지 않을 수 있다. 그래서 아래처럼 나눈다.

- **쓰기:** 방송 등록·수정·삭제, 송출 시작·종료, 채팅 작성, 후원 확정은 모두 Next.js 서버를 거친다. (결정 12에서 채팅 수정과 삭제를 뺐다.) 서버가 로그인 토큰과 소유자를 확인한 뒤 Firebase 관리자 SDK로 쓴다.
- **읽기:** 방송 목록, 댓글, 방송 상태는 브라우저가 실시간 구독으로 바로 받는다.
- **보안 규칙:** 브라우저의 직접 쓰기를 모두 막는다.

### 뺀 후보와 이유

| 후보 | 뺀 이유 |
|---|---|
| Neon (Postgres) | 프로젝트가 멈추지 않는 점은 좋다. 하지만 로그인과 실시간 댓글을 따로 만들어야 해서 1인 2주 일정에 불리하다 |
| Supabase | 무료 프로젝트는 7일 동안 사용이 적으면 멈춘다(공식 문서). 심사 도중에 서비스가 멈출 수 있다 |
| Firebase Cloud Storage | 2026년 2월 3일부터 유료 플랜(Blaze)에서만 쓸 수 있다(공식 FAQ). 무료 플랜 프로젝트는 저장소에 접근하면 오류가 난다. 녹화 영상은 용량도 커서 R2에 저장한다 |

### 위험과 확인할 것

| 위험 | 대응 |
|---|---|
| Firestore 무료 한도는 하루 읽기 5만 번, 쓰기 2만 번이다. 시청자가 실시간 댓글을 오래 구독하면 읽기가 빨리 쌓인다 | 심사 규모에서는 충분하다고 본다(추론). 심사 전에 사용량을 확인한다 |
| Vercel 무료 플랜은 비상업적·개인 용도만 허용한다 | 공모 제출물은 개인 프로젝트라 문제없다고 판단했다(추론) |
| LiveKit 녹화를 R2로 보내는 설정 | LiveKit 공식 문서가 Cloudflare R2를 지원 저장소로 적고 있다. 주소 `https://<계정ID>.r2.cloudflarestorage.com`을 넣고 `force_path_style`을 켠다. 실제 업로드는 한 번 테스트한다 |

## 결정 3. 후원 배분: 방송자 80%, 나비 20%

- **결정일:** 2026-11-06
- **결정:** 모든 방송자에게 같은 비율을 적용한다. 방송자가 후원의 80%를 받고, 나비가 20%를 받는다. 결제 수수료는 나비 몫에서 낸다.
- **바뀜 (2026-11-07):** 결정 9에서 등급별 비율(80~88%)로 바꿨다. 가장 낮은 등급이 80%라서 아래 이유는 그대로 유효하다.

### 다른 서비스의 배분

| 서비스 | 방송자가 받는 몫 |
|---|---|
| 치지직 | 등급별 60~80%다. 루키 60%, 프로·챌린저 70%, 파트너 80%다 |
| 유튜브 슈퍼챗 | 70%다. 카드 수수료는 유튜브가 낸다 |
| 트위치 비츠 | 비율이 아니라 1비츠당 1센트로 고정이다. 자료마다 달라서 확인이 필요하다 |

### 비교한 후보

| 후보 | 방송자 | 나비 | 뺀 이유 |
|---|---|---|---|
| 단일 90% | 90% | 10% | 결제 수수료를 빼면 나비 몫이 약 7%만 남는다 |
| 등급제 | 60~80% | 20~40% | "입문 방송자에게 더 많이 준다"는 차별점이 사라진다. 등급 기준도 따로 만들어야 한다 |

### 80%를 고른 이유

- 처음 방송하는 사람도 치지직 최상위 등급(파트너)과 같은 몫을 받는다. 유튜브보다도 높다. 그래서 경쟁 분석의 차별화 기회인 "입문 방송자에게 후원 배분을 더 준다"와 그대로 이어진다.
- 설명이 쉽다. 화면과 기획서에 "후원의 80%가 방송자에게 갑니다" 한 줄이면 된다.
- 방송자가 더 벌수록 나비의 몫도 함께 는다. 그래서 방송자와 나비의 이익이 같은 방향을 본다.

### 이번 개발에서 다루는 범위

- 정산(실제 출금)은 개발 범위 밖이다. 그래서 배분 비율은 후원 내역 화면에 표시만 한다. 예를 들어 "받은 후원 10,000원, 예상 수익 8,000원"처럼 보여준다.
- 결제 서비스는 토스페이먼츠 테스트 모드를 기본으로 한다. 사업자 등록 없이 개인이 테스트 키를 받을 수 있는지는 확인하지 못했다. 개발을 시작하기 전에 [토스페이먼츠 개발자 문서](https://docs.tosspayments.com)에서 확인한다.
- 같은 승인 통지가 반복되어도 한 번만 적립되도록, 결제 번호를 Firestore 문서 ID로 쓰고 트랜잭션으로 저장한다.

## 결정 4. 시청자가 다시 오는 이유: 아는 방송자가 켜면 알려준다 (방향만)

- **결정일:** 2026-11-06
- **이번 개발:** 넣지 않는다. 기획서에 방향만 적는다.

### 방향

시청자는 처음에 대부분 방송자가 보낸 링크로 들어온다. 그래서 다시 오는 가장 자연스러운 이유는 "그 방송자가 또 방송을 켰다"는 것이다.

1. 시청자가 방송자를 팔로우한다.
2. 방송자가 방송을 켠다.
3. 팔로워에게 알림이 간다.
4. 시청자가 다시 들어온다.

팔로우는 무료 관계다. 채널 구독은 이 관계를 응원과 수익으로 바꾸는 다음 단계다. 치지직도 팔로잉 목록과 알림 화면을 따로 둔다(레퍼런스 파일 이름 기준).

### 이번 개발에서 뺀 이유

웹 푸시 알림은 아이폰에서 홈 화면에 추가한 경우에만 동작하는 것으로 알고 있다. 확인이 필요하다. 2주 안에 다루기에는 위험하다.

## 결정 5. 작은 방송 발견: 방송 목록을 "방송 중 먼저, 그다음 최근에 켠 순서"로 정렬한다

- **결정일:** 2026-11-06
- **이번 개발:** 목록 정렬만 넣는다. 방송 목록은 필수 기능이라 정렬 기준을 어차피 정해야 한다.

### 이번 개발에 넣는 것

- 방송 목록은 시청자 수로 정렬하지 않는다. 방송 중인 방송을 먼저 보여주고, 그 안에서는 최근에 켠 방송을 위에 둔다.
- 치지직 홈은 시청자가 많은 방송을 위에 크게 보여준다. 그래서 시청자가 0명인 방송은 보이지 않는다. 나비는 방금 켠 방송이 맨 위에 온다.
- 추가 비용이 없다. Firestore에서 방송 상태와 시작 시각으로 정렬하면 된다.
- 심사자가 방금 켠 테스트 방송이 목록 맨 위에 바로 보인다.

### 나중에 할 것 (방향만)

- 시청자가 적은 방송을 목록에 섞어 보여준다.
- "아무 방송이나 들어가기" 버튼을 둔다.
- 태그로 방송을 찾게 한다.

이 기능들은 방송이 많아져야 의미가 있다. 그래서 기획서에 방향으로만 적는다.

## 결정 6. LiveKit은 무료 플랜으로 간다. 녹화는 테스트 용도로만 쓴다

- **결정일:** 2026-11-06
- **결정:** 심사 기간에도 LiveKit 유료 플랜(Ship, 월 50달러)을 쓰지 않는다. 녹화는 기능이 작동하는지 확인하는 용도로만 짧게 쓴다. 테스트 녹화 파일은 확인한 뒤 지운다.
- **이유:** 녹화는 선택 기능이다. 개발자는 녹화가 작동하는지만 확인하고, 심사자도 짧게 테스트만 해 볼 것으로 본다.

### 주의할 점

- LiveKit 무료 녹화 60분은 **녹화한 시간**으로 줄어든다. R2에서 파일을 지우면 저장 용량은 돌아오지만 LiveKit 녹화 시간은 돌아오지 않는다.
- 그래서 개발 중 녹화 테스트는 한 번에 1~2분으로 짧게 한다. 심사자가 쓸 녹화 시간을 남겨 둔다.
- 녹화 한도를 넘으면 새 녹화가 실패한다. 이때 방송 자체는 계속되어야 한다. 화면에는 "녹화를 시작하지 못했다"고 알려 준다.

## 결정 7. 회원, 채팅, 후원, 녹화의 운영 정책

- **결정일:** 2026-11-07
- **배경:** 기능 명세와 피그마 와이어프레임을 비교하다가 정하지 않은 운영 규칙이 나왔다. 자세한 동작은 [07 기능 명세](07-feature-spec.md)의 4-1, 4-4, 4-7~4-11에 적었다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 종료된 방송의 채팅 | 쓸 수 없다. 읽기만 한다. 이미 쓴 채팅의 수정과 삭제는 된다. (결정 12에서 수정과 삭제를 뺐다) | 와이어프레임(E-10, G-6, I-6)과 맞춘다. 방송이 끝난 뒤의 대화는 방송자가 보지 않는다 |
| 종료된 방송의 후원 | 받지 않는다. 다시보기에서도 받지 않는다 | 후원은 방송 중의 반응이다. 끝난 방송의 결제를 처리하면 예외 경우만 늘어난다 |
| 채팅 걸러내기 | 금칙어가 있으면 "부적절한 표현이 감지되어 숨긴 채팅이에요"로 숨긴다. 응원 한마디도 같다 | 처음 방송하는 사람은 채팅을 직접 관리할 여유가 없다. 치지직도 비슷하게 숨김 문구를 보여준다 |
| 닉네임 | 2~12자, 한글·영문·숫자, 중복 불가, 가입 뒤 한 번만 변경 | 닉네임을 자주 바꾸면 채팅과 후원에서 누가 누구인지 알기 어렵다 |
| 회원가입 | 만 14세 이상, 이용약관, 개인정보 수집·이용에 동의를 받는다. 모두 필수다 | 이메일과 후원 기록을 모으므로 동의가 필요하다 |
| 비밀번호 찾기, 회원 탈퇴 | 둘 다 만든다 | 계정이 있는 서비스라면 기본으로 있어야 한다 |
| 마이크 없이 방송 | 경고한 뒤 시작은 허용한다. 방송이 끝날 때까지 닫을 수 없는 안내를 보여준다 | 마이크 없이 탭 소리만 보내는 방송도 있다. 하지만 방송자가 모르고 켜는 일은 막는다 |
| 탭 제목 숫자 | 빼기로 했다 | 효과가 분명하지 않다. 송출 화면의 후원 알림으로 충분하다 |
| 지운 방송의 후원 | 방송자의 내 방송 관리와 후원한 시청자의 내 후원 내역에 남긴다 | 돈이 오간 기록이다 |
| 녹화 중인 방송 삭제 | 녹화 중이거나 처리 중이면 지울 수 없다 | 늦게 온 녹화 완료 알림이 주인 없는 파일을 남기지 않게 하기 위해서다 |
| 녹화 공개 여부 | 처음은 비공개다. 방송자가 공개로 바꿔야 다시보기 목록에 나온다 | 방송자가 보여주고 싶지 않은 장면이 녹화될 수 있다 |
| 테스트 계정 바로 로그인 | 로그인 화면에 그대로 둔다. 닉네임 변경과 탈퇴는 막는다 | 공모 요강이 요구하고, 심사자가 채점할 때 쓴다 |

### 이 결정으로 늘어나는 일

- 화면이 새로 생긴다. 비밀번호 찾기, 이용약관, 개인정보 처리방침, 내 정보(닉네임 변경, 내 후원 내역, 탈퇴)다.
- 비공개 녹화 때문에 R2 파일을 공개 주소로 둘 수 없다. 서버가 재생할 때마다 잠깐 쓰는 주소를 만들어 준다.
- 금칙어 목록과 약관 문서를 직접 준비해야 한다.
- 일정이 모자라면 이 문서 위쪽의 "일정이 모자랄 때 빼는 순서" 표를 따른다. 이번에 늘어난 일 가운데 약관 동의와 비밀번호 찾기는 빼지 않는다.

## 결정 8. 후원은 포인트(꿀)를 충전해서 한다

- **결정일:** 2026-11-07
- **결정:** 시청자가 꿀을 충전해 두고 꿀로 후원한다. 후원 창은 치지직처럼 아래에서 올라오는 창으로 만들고, 채팅 후원과 미션 후원 탭, 익명 후원, 더하기 금액 버튼을 넣는다. 채팅 읽어주기(TTS)는 화면만 그린다. 자세한 동작은 [07 기능 명세](07-feature-spec.md) 4-8에 있다.
- **바뀐 것:** 결정 3과 00 브리핑의 시청자 약속 "충전 없이 바로 후원한다"를 바꾼다. 잔액이 모자라면 "충전하고 후원하기" 한 번으로 끝나게 해서 단계 수를 줄인다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 포인트 | 꿀 1개 = 1원, 결제할 때 부가세 10%를 더한다. 이름은 임시다 | 치지직 치즈와 같은 구조라 시청자에게 익숙하다 |
| 충전하고 후원하기 | 모자란 만큼 가장 작은 충전 단위로 충전하고, 승인되면 같은 트랜잭션에서 후원한다 | 공모 요강의 "후원 대상과 금액을 고르고 테스트 결제를 요청한다"를 이 흐름으로 채운다 |

| 익명 후원 | 다른 사람에게는 "익명"으로 보이고 서버는 실제 후원자를 기록한다 | 운영정책 위반을 추적할 수 있어야 한다 |
| 충전 취소 | 충전 후 7일 안, 하나도 쓰지 않은 충전 건만 취소한다. 먼저 충전한 꿀부터 쓴다 | 어느 충전 건을 썼는지 계산할 수 있어야 취소 조건을 판단할 수 있다 |
| 채팅 읽어주기 | 화면만 그린다 | 목소리를 고르려면 외부 음성 서비스가 필요하다 |
| 안내 문구 | 치지직 안내의 구성을 참고하되 문장은 나비 정책에 맞춰 새로 쓴다 | 다른 서비스의 약관 문장을 그대로 옮기면 저작권 문제가 생길 수 있다. 치지직 문구에는 나비에 없는 정책(모바일 웹 사용 불가, 앱 마켓 환불 등)도 들어 있다 |

### 위험

- **일정:** 지갑, 충전 취소, 미션 상태 처리가 새로 생긴다. 마감(11월 19일)까지 12일 남았다. 일정이 모자라면 미션 후원, 충전 취소, 익명 순서로 뺀다(위쪽 "일정이 모자랄 때 빼는 순서" 표의 14~16번). 후원은 공모 선택 항목이다. 후원을 만든다면 "충전하고 후원하기"와 한 번만 처리하기는 그 선택 항목의 요건이라 빼지 않는다.
- **심사 흐름:** 잔액이 있으면 결제창이 뜨지 않는다. 심사자가 결제 검증을 확인하려면 꿀이 0인 계정으로 시작해야 한다. README에 테스트 시청자 계정의 잔액을 0으로 되돌리는 방법을 적는다.

## 결정 10. Docker는 지금 준비만 하고, 시간이 남으면 제출 전에 붙인다

- **결정일:** 2026-11-07
- **배경:** 공모 요강에는 Docker 요구가 없다. Docker를 쓰려는 목적은 두 가지다. 하나는 제출한 뒤 심사자가 바로 써 보게 하는 것이고, 다른 하나는 로컬에서 편하게 테스트하는 것이다.
- **결정:** 지금은 Docker 파일을 만들지 않는다. 대신 스캐폴딩할 때 아래 규칙을 지켜서, 나중에 Docker를 붙일 때 코드를 고칠 일이 없게 한다. 필수 기능이 끝나고 제출 2~3일 전에 시간이 남으면 Docker를 붙인다.

### 지금 넣지 않는 이유

| 이유 | 설명 |
|---|---|
| 일정 | 마감까지 12일이고 혼자 만든다. 처음 설정에 반나절 이상 들고, 그 뒤로도 실제 서비스와 로컬 대체품 두 환경을 계속 맞춰야 한다 |
| 심사자에게 주는 이득이 작다 | 심사자는 배포 주소로 본다. 아이폰 카메라는 HTTPS 주소에서만 켜지므로 아이폰 테스트도 배포 주소에서만 된다 |
| 아끼는 한도가 작다 | 가장 빠듯한 한도는 LiveKit 녹화 월 60분이다. 녹화 기능(Egress)은 로컬에 띄우기 무거워서 어차피 클라우드에서 테스트한다. LiveKit 참가자 5,000분과 Firestore 하루 읽기 5만 번은 짧게 테스트하면 충분하다 |
| 환경 차이 | 에뮬레이터와 실제 서비스는 동작이 조금씩 다르다. 차이가 생기면 원인을 찾는 데 시간이 든다 |

### 스캐폴딩할 때 지킬 것 (체크리스트)

| 무엇을 | 어떻게 | 나중에 Docker에서 하는 일 |
|---|---|---|
| 서비스 주소와 키 | 코드에 직접 쓰지 않고 모두 환경 변수로 받는다. `.env.example`에 목록을 둔다 | 환경 변수만 바꿔 로컬 대체품을 가리킨다 |
| Firebase | 에뮬레이터 주소 환경 변수가 있으면 초기화 코드가 에뮬레이터에 붙게 한다 | Firebase 에뮬레이터(Firestore, Auth)를 쓴다 |
| LiveKit | 서버 주소, API 키, 비밀 키를 환경 변수로 받는다 | LiveKit 개발 서버(`livekit-server --dev`)를 쓴다 |
| 녹화 저장소 | S3 주소와 경로 방식(`force_path_style`)을 환경 변수로 받는다. R2에도 필요한 설정이다 | MinIO를 쓴다 |
| 녹화 켜고 끄기 | 녹화 기능을 환경 변수 하나로 끌 수 있게 한다 | 로컬에서는 녹화를 끈다 |
| 테스트 계정 | 테스트 계정과 상태를 만드는 시드 스크립트를 따로 둔다. 예를 들어 꿀 0인 시청자, 애벌레 승급 직전 방송자다 | 띄울 때 시드 스크립트를 한 번 실행한다 |
| Node 버전 | `.nvmrc`와 `package.json`의 `engines`에 고정한다 | Docker 이미지에 같은 버전을 쓴다 |

### 나중에 붙일 때 추가할 것

- `Dockerfile`: Next 앱
- `docker-compose.yml`: Next 앱, Firebase 에뮬레이터, LiveKit 개발 서버, MinIO
- README의 "로컬에서 키 없이 실행하기"
- 토스페이먼츠는 로컬 대체품이 없다. 문서에 공개된 테스트 키를 `.env.example`에 넣는다. 웹훅은 로컬까지 오지 않지만, 결제 완료 화면이 같은 "충전 확정" 함수를 부르므로 충전은 된다(07 7장).

### 그 전에 한도가 걱정되면

LiveKit 테스트가 잦아지면 LiveKit 개발 서버 하나만 `docker run` 한 줄로 띄워서 쓴다. 이때도 위 규칙 덕분에 환경 변수만 바꾸면 된다.

### 확인하지 않은 것

- 반나절이라는 설정 시간은 추정이다.
- Firebase 에뮬레이터는 공식 Docker 이미지가 없는 것으로 안다. Node와 Java가 든 이미지에 firebase-tools를 설치해야 할 것으로 본다.
- LiveKit 개발 서버와 Firebase 에뮬레이터를 실제로 띄워 보지 않았다.

| 구조 | 목업은 실제 구현과 같은 인터페이스 뒤에 둔다. 나중에 실행기나 연결 대상만 바꾸면 실제 기능이 된다 |
| 표시 | 화면에 "테스트(목업)"를 붙인다. README에 목업 목록과 실제로 바꾸는 방법을 적는다 |
| 순서 | 필수 기능이 모두 끝난 뒤에 만든다. 일정이 모자라면 목업부터 뺀다 |

### 목업 후보와 우선순위

| 순서 | 목업 | 목업인 이유 | 이번 결정에서 |
|---|---|---|---|
| 1 | 예약 작업 실행기 | 실제 시간이 지나야 실행된다 | 설계한다 |
| 2 | 정산 송금 | 결제대행사 지급대행 계약이 필요하다 | 설계한다 |
| 3 | 등급 하락, 보관 기간이 지난 다시보기 삭제 | 실제 시간이 지나야 실행된다 | 후보로만 둔다 |
| 4 | 정산 정보 본인 인증 | 본인 인증 서비스 계약이 필요하다 | 후보로만 둔다. 이번에는 시드 스크립트로 테스트 계좌를 넣는다 |
| 5 | 광고(5초 뒤 건너뛰기) | 광고 계약이 필요하다 | 후보로만 둔다 |

- 채널 구독은 정기 결제가 얽혀 있어 목업이라도 일이 크다. 후보에서 뺀다.
- 채팅 읽어주기는 브라우저의 음성 합성 기능으로 실제로 만들 수 있어 목업 대상이 아니다. 아이폰에서 되는지는 확인하지 않았다.

### 정산 구현 범위

| 단계 | 이번 개발 | 설명 |
|---|---|---|
| 정산 계산 | 실제로 만든다 | 방송자와 기간을 넣으면 아직 정산되지 않은 확정 후원의 방송자 몫 합계를 돌려준다. 내 방송 관리의 예상 정산 금액도 이 함수로 구한다 |
| 정산 확정 | 실제로 만든다 | 계산 결과를 정산 기록으로 저장하고, 들어간 후원에 정산 표시를 남긴다. 같은 후원은 두 번 정산되지 않는다 |
| 예약 작업 | 목업 | 매달 25일 실행 대신, 테스트 방송자 계정의 "지금 정산해 보기" 버튼이 같은 작업을 실행한다 |

| 정산 정보 | 시드로 대신한다 | 등록 화면과 본인 인증은 만들지 않는다. 테스트 계좌를 시드 스크립트로 넣는다 |

### 심사 기간에 정산할 "지난달"이 없는 문제

- 정책은 "지난달 확정분을 이번 달 25일에 지급"이다. 심사 시점(11월 말)의 지난달인 10월에는 후원 기록이 없다.
- 그래서 테스트 실행은 기간을 "이번 달 1일부터 지금까지"로 잡는다. 실제 예약 실행은 "지난달 1일부터 말일까지"로 잡는다.
- 두 경로 모두 같은 정산 확정 함수를 부른다. 기간만 다르다.

### 바뀐 것

- 결정 9의 "실제 송금: 범위 밖, 예상 금액만 표시"를 "정산 확정까지 실제, 송금은 목업"으로 바꿨다.
- 00 브리핑 8장의 빼는 순서(녹화와 다시보기, 후원, 채팅)보다 정산 확정과 목업을 **먼저** 뺀다. 정산 계산은 내 방송 관리 카드에 필요하므로 빼지 않는다. 전체 순서는 위쪽 "일정이 모자랄 때 빼는 순서" 표에 있다.

### 위험

- **일정:** 하루에서 하루 반 정도로 추정한다. 코드 작성은 빠르게 할 수 있지만, 화면, 피그마, README, 실제 확인에 드는 시간은 줄지 않는다.
- **오해:** 목업이 실제 기능처럼 보이면 심사에서 불리할 수 있다. 화면과 README에 목업임을 분명히 적는다.
- **가산점:** 공모 요강에 목업 관련 기준이 있는지는 확인하지 않았다.

## 결정 12. 채팅은 LiveKit 연결로 전달하고, 수정과 삭제는 만들지 않는다

- **결정일:** 2026-11-07
- **배경:** 공모 요강의 "댓글"을 나비에서는 실시간 채팅으로 만든다(07 4-7). 채팅이라면 웹소켓처럼 연결을 유지한 채 바로 주고받는 방식이 맞다. 채팅에는 보통 수정 기능이 없다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 전달 방식 | 시청자와 방송자가 영상 때문에 이미 맺고 있는 LiveKit 연결로 채팅을 전달한다. LiveKit은 웹소켓과 WebRTC로 연결을 유지한다 | 새 서버가 필요 없다. Vercel은 웹소켓 서버를 띄울 수 없어서, 직접 만들면 항상 켜진 서버를 따로 두어야 한다 |
| 저장 | 채팅은 서버가 확인한 뒤 Firestore에 저장한다. 늦게 들어온 사람의 지난 채팅, 다시보기 채팅, 탈퇴 처리는 Firestore 기록을 쓴다 | 연결로 오간 메시지는 남지 않는다 |
| 보내는 길 | 브라우저는 LiveKit으로 직접 보내지 못한다. 서버에 보내면 서버가 로그인, 방송 상태, 금칙어, 도배를 확인하고 저장한 뒤 LiveKit 서버 API로 방 전체에 보낸다 | 서버 확인을 건너뛰는 메시지를 막는다. 접속 권한에서 데이터 보내기를 끈다 |
| 수정과 삭제 | 만들지 않는다. 내 채팅도 지울 수 없다. **결정 32에서 되돌려 지금은 만든다** | 사용자 결정이다. 채팅은 흘러가는 대화라 수정과 삭제가 없는 서비스가 많다 |
| 도배 막기 | 한 사람이 같은 방송에 1초에 1개까지 보낼 수 있다. 넘으면 "조금 천천히 보내 주세요"를 보여준다 | 채팅은 짧은 글을 연달아 보내는 일이 많다. 저장 비용도 줄어든다. 1초는 임시값이다 |

### 다른 후보와 뺀 이유

| 후보 | 뺀 이유 |
|---|---|
| Firestore 실시간 구독 (기존) | 동작은 한다. 다만 시청자마다 새 채팅을 하나씩 읽어서 "채팅 수 × 시청자 수"만큼 읽기가 쌓인다. LiveKit으로 바꾸면 시청자가 들어올 때 한 번만 읽는다 |
| 웹소켓 서버 직접 운영(Render, Fly 등) | 항상 켜진 서버가 필요하다. 무료 플랜은 잠들 수 있어 심사 도중 끊길 수 있다. 결정 2의 예상 비용 0원과 일정에 부담이 크다 |

### 잃는 것

- 공모 요강 체크리스트의 **선택 항목 두 개를 채우지 않는다.** "댓글 작성, 조회, 수정, 삭제"와 "댓글 수정·삭제 시 서버에서 작성자 권한 검증"이다(07 11장).
- 작성자 권한 검증은 방송 수정·삭제, 후원, 미션 처리에서 같은 수준으로 보여 줄 수 있다. README에 이 대응을 적는다.

### 바뀐 것

- 결정 2의 "읽기: 댓글은 브라우저가 실시간 구독으로 받는다"를 바꾼다. 채팅, 후원 항목, 미션 상태 변화는 LiveKit으로 받는다. 방송 상태와 홈 목록은 지금처럼 Firestore 실시간 구독으로 받는다.
- 결정 7의 "종료된 방송에서도 이미 쓴 채팅의 수정과 삭제는 된다"를 지운다.
- 피그마의 G-9(내 채팅 메뉴), G-10(채팅 수정 중), G-11(채팅 삭제 확인)을 지운다.

### 위험

- LiveKit으로 보내는 데 실패하면, 채팅은 저장됐지만 다른 사람 화면에 바로 뜨지 않을 수 있다. 서버는 한 번 다시 보낸다. 브라우저는 다시 연결될 때 Firestore에서 최근 채팅을 불러와 빠진 것을 채운다.
- LiveKit 데이터 메시지의 크기 한도와 무료 플랜 요금 계산은 확인하지 않았다. 채팅은 200자라 한도에 걸리지 않을 것으로 본다.

## 결정 13. 운영자 화면을 만들고, 신고와 제재를 함께 만든다

- **결정일:** 2026-11-07
- **배경:** 09 약관과 07의 후원 안내 문구는 "나비가 경고, 숨김, 이용 제한, 지급 보류를 할 수 있다"고 약속한다. 그런데 이 일을 실행할 화면과 권한이 없다. 시청자가 문제를 알릴 신고 기능도 없다. 방송자에게는 자기 방송을 관리하는 스튜디오(내 방송 관리)가 있지만, 플랫폼을 운영하는 사람의 화면은 없다.
- **이번 개발:** 기획, 설계, 디자인을 모두 한다. 자세한 동작은 [07 기능 명세](07-feature-spec.md) 4-13~4-15에 있다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 범위 | 운영자 화면(대시보드, 방송, 회원, 정산, 충전, 예약 작업, 테스트 계정, 운영 기록), 신고, 방송자 활동 제한, 운영자 제재, 이의 제기를 모두 만든다 | 사용자 결정이다. 약관에 적은 운영 행위를 실제로 실행할 수 있어야 한다 |
| 운영자 권한 | Firebase 계정에 "운영자" 표시를 붙인다. 표시는 서버 스크립트로만 붙인다. 서버가 모든 운영자 요청에서 이 표시를 확인한다 | 화면에서 권한을 줄 수 있으면 권한이 새어 나갈 수 있다 |
| 운영자 화면 위치 | `/admin` 아래에 둔다. PC만 지원한다 | 운영자는 책상에서 일한다. 휴대폰 화면까지 그리면 일이 두 배가 된다 |
| 신고 대상 | 채팅 메시지(후원 메시지 포함), 방송, 사용자 프로필 세 가지다 | 사용자 결정이다. 다시보기 신고는 넣지 않는다 |
| 방송자 활동 제한 | 방송자가 자기 방송에서 특정 시청자의 채팅을 막는다. 기간은 1일, 7일, 영구다. 방송자가 언제든 풀 수 있다 | 입문 방송자가 악성 시청자를 운영자를 기다리지 않고 스스로 막을 수 있다. 치지직의 "활동 제한"과 같은 역할이다 |
| 운영자 제재 단계 | 경고, 채팅 금지(1일·7일), 방송 금지(7일·30일), 영구 정지 | 위반 정도에 맞춰 조치할 수 있다 |
| 이의 제기 | 제재 하나에 한 번 이의를 제기할 수 있다. 운영자가 받아들이면 제재를 취소하고, 거절하면 이유를 적는다 | 잘못된 제재를 바로잡을 길이 있어야 한다 |
| 제재 기간이 끝나는 처리 | 예약 작업을 쓰지 않는다. 요청이 올 때마다 서버가 끝나는 시각을 확인한다 | 정해진 시각에 도는 작업 없이도 기간 제재가 정확히 끝난다 |
| 심사자 접근 | 로그인 화면에 "테스트 운영자로 로그인"을 둔다 | 심사자가 신고 처리와 제재를 직접 해 볼 수 있다 |
| 테스트 계정 보호 | 테스트 방송자와 테스트 시청자는 제재할 수 없다. 대신 "제재 연습용 계정"을 두고, 신고가 쌓인 상태로 시드한다. 테스트 운영자는 이 계정을 초기화할 수 있다 | 한 심사자가 테스트 계정을 정지하면 다음 심사자가 쓸 수 없다 |
| 정산 테스트 실행 위치 | 결정 11의 "지금 정산해 보기(테스트)"를 방송자 화면에서 운영자 화면으로 옮긴다 | 실제로도 정산을 실행하는 사람은 운영자다 |
| 운영 기록 | 운영자가 한 모든 일을 누가, 언제, 무엇을, 왜 했는지 남긴다. 지울 수 없다 | 운영자의 권한 남용을 나중에 확인할 수 있어야 한다 |

### 바뀐 것

- 결정 11의 정산 테스트 버튼 위치를 운영자 화면으로 바꿨다.
- 07 4-7의 금칙어 목록을 코드 파일에서 Firestore 설정 문서로 옮긴다. 운영자가 화면에서 고칠 수 있게 하기 위해서다.
- 테스트 계정 바로 로그인 버튼이 두 개에서 세 개(방송자, 시청자, 운영자)가 된다.

### 위험

- **일정:** 이 결정으로 화면이 가장 많이 늘어난다. 운영자 화면 10여 개, 시청자의 신고·제재 화면, 방송자의 활동 제한 화면이다. 필수 기능이 끝난 뒤에 만들고, 일정이 모자라면 아래 순서로 뺀다.
  1. 충전·결제 내역, 예약 작업 기록 화면
  2. 금칙어 관리 화면(코드 파일로 되돌린다)
  3. 이의 제기
  - 신고, 운영자 제재, 방송자 활동 제한, 운영 기록은 빼지 않는다. (결정 25에서 바뀜: 공모 선택 항목보다 먼저 뺀다. 위쪽 빼는 순서 표의 18번)
- **권한:** 운영자 권한이 새면 모든 계정을 정지할 수 있다. 운영자 표시는 스크립트로만 붙이고, 테스트 운영자는 운영자 권한을 바꿀 수 없다.
- **신고 남용:** 같은 사람이 같은 대상을 여러 번 신고할 수 없다. 한 사람은 하루 20건까지 신고할 수 있다. 20은 임시값이다.

|---|---|---|
| 백엔드 위치 | Vercel 위의 Next.js 서버 함수(Route Handler)로 둔다. 배포하는 앱은 하나다 | 결정 2와 12를 지킨다. 항상 켜진 서버가 없어서 비용이 0원이고, 심사 도중 서버가 잠들 위험이 없다 |
| 코드 나누기 | 모노레포(pnpm workspace)에 `apps/web`(Next 앱), `packages/core`(서버 로직), `packages/shared`(입력 검사 스키마, 타입, 상수)를 둔다 | 화면 코드와 서버 로직이 폴더 단위로 나뉜다. `core`는 브라우저에서 불러오지 못하게 막는다 |
| API 입구의 역할 | `apps/web/app/api`는 입력 검사, 로그인 확인, `core` 호출만 한다. 로직은 `core`에만 둔다 | 나중에 서버를 따로 띄워야 하면 `core`를 그대로 옮기면 된다 |
| 엔진엑스·게이트웨이 | 쓰지 않는다 | HTTPS와 정적 파일 전달은 Vercel이 한다. 영상은 LiveKit Cloud로 바로 간다. 서버가 하나라 요청을 나눠 보낼 곳이 없다. 로그인 확인과 도배 제한은 서버 함수 안에서 한다. 엔진엑스를 두려면 항상 켜진 서버가 따로 필요하다 |

### 뺀 후보와 이유

| 후보 | 뺀 이유 |
|---|---|
| 백엔드 서버를 따로 배포(`apps/api`) | 항상 켜진 서버가 필요하다. 무료 서버는 잠들 수 있어 심사 도중 끊길 수 있다. 다른 주소끼리 요청을 허용하는 설정(CORS), 토큰 전달, 배포 두 벌이 추가로 생긴다. 1인 12일 일정에 부담이 크다 |
| Turborepo 같은 모노레포 빌드 도구 | 패키지가 셋뿐이라 pnpm workspace만으로 충분하다. 빌드가 느려지면 그때 붙인다 |

### 위험

- Next 앱이 내부 TypeScript 패키지를 불러오려면 `transpilePackages` 설정이 필요하다. 스캐폴딩할 때 한 번 확인한다.
- Vercel 서버 함수는 오래 걸리는 작업에 한도가 있다(결정 2의 최대 5분). 정산 계산은 심사 규모에서 이 안에 끝난다고 본다(추론).

## 결정 15. PC 방송에서만 화면과 카메라를 함께 보낼 수 있게 한다

- **결정일:** 2026-11-07
- **배경:** PC 방송자의 바람은 둘로 나뉜다. 화면만 보여주고 싶은 사람이 있고, 화면과 얼굴을 함께 보여주고 싶은 사람이 있다. 그래서 두 가지를 모두 지원한다. 휴대폰 브라우저는 화면 공유를 사실상 지원하지 않는다. 그래서 이 기능은 PC에서만 쓸 수 있다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 쓸 수 있는 곳 | PC의 "PC 화면 공유" 방송에서만 쓴다 | 휴대폰 브라우저는 화면 공유를 지원하지 않는다 |
| 켜는 방법 | 방송 만들기에서 "PC 화면 공유"를 고르면 "내 얼굴도 같이 보여주기" 스위치가 나온다. 기본은 꺼짐이다 | 송출 방식 선택지 두 개를 그대로 둘 수 있다 |
| 보내는 방법 | 화면 영상과 카메라 영상을 LiveKit으로 따로 보낸다. 시청 화면에서 큰 화면 위 오른쪽 아래에 작은 카메라 창을 얹는다 | LiveKit은 한 사람이 영상 여러 개를 보내는 것을 기본으로 지원한다. 서버 쪽에서 바꿀 것이 없다 |
| 녹화 | LiveKit의 방 합성 녹화(방에 들어온 영상을 영상 하나로 합쳐 녹화하는 방식)를 쓴다. 기본 배치 중 바둑판형(grid)을 쓴다. 방에서 영상을 보내는 사람은 방송자 한 명뿐이라, 화면만 보내면 화면이 꽉 차게, 화면과 카메라를 보내면 둘이 나란히 녹화된다. 화면만 하는 방송과 휴대폰 카메라 방송도 같은 방식으로 녹화한다 | 녹화 코드가 한 갈래로 줄어든다. 방송 방식마다 어떤 영상을 녹화할지 고를 필요가 없다. 녹화는 테스트에서 동작을 확인하는 용도라서(결정 6) 시청 화면과 같은 "작은 카메라 창" 배치까지는 만들지 않는다 |
| 저장 데이터 | 새 필드를 만들지 않는다 | 카메라 창은 LiveKit에 카메라 영상이 들어와 있는지로 판단한다. 방송 중에 카메라를 껐다 켜도 저장할 것이 없다 |
| 일정 | 필수 기능이 끝난 뒤에 만든다. 일정이 모자라면 가장 먼저 뺀다 | 공모 요강에 없는 기능이다 |

### 뺀 후보와 이유

| 후보 | 뺀 이유 |
|---|---|
| 방송자 브라우저에서 화면과 카메라를 영상 하나로 합쳐서 보내기(캔버스) | 탭 공유를 하면 방송자는 공유한 탭으로 넘어가고, 나비 탭은 뒤로 숨는다. 크롬은 숨은 탭의 그리기 작업을 멈추거나 크게 늦춘다. 그래서 시청자 화면이 멈추거나 끊길 가능성이 크다(추론). 피하려면 별도 작업 스레드에서 합쳐야 해서 일이 커진다 |
| 송출 방식에 세 번째 선택지 "화면 + 카메라" 추가 | 스위치 하나로 같은 일을 할 수 있다. 선택지가 늘면 방송 만들기 화면이 복잡해진다 |

### 위험

- 방송자가 올려 보내는 데이터가 늘어난다. 인터넷이 느리면 화질이 떨어질 수 있다. LiveKit이 화질을 자동으로 낮춘다.
- 시청자가 받는 데이터도 늘어난다. LiveKit 무료 플랜의 전송량 한도에 얼마나 영향을 주는지 확인하지 않았다.
- 바둑판형 배치에서 화면과 카메라가 실제로 어떻게 나뉘는지는 확인하지 않았다. 개발할 때 1~2분짜리 녹화로 한 번 확인한다. 보기 나쁘면 녹화 배치용 페이지(커스텀 템플릿)를 만들지 다시 정한다.
- 방 합성 녹화는 무료 플랜의 "트랜스코드 시간" 월 60분에서 빠진다(LiveKit 가격표). 외부 송출을 받아들이는 기능(stream import)과 함께 쓰는 한도지만, 나비는 그 기능을 쓰지 않는다. 화면만 녹화하던 이전 방식과 같은 한도에서 빠지는지는 가격표에 나오지 않는다.
- 카메라 권한을 거부해도 화면만으로 방송할 수 있어야 한다. 이 경우 "카메라를 켜지 못했어요. 화면만 송출돼요"를 보여준다.

## 결정 17. 백엔드는 가벼운 헥사고날 구조로 만든다

- **결정일:** 2026-11-07
- **배경:** 서버 로직은 `packages/core`에 둔다(결정 14). 나비는 외부 서비스가 네 개(Firestore, LiveKit, R2, 토스페이먼츠)다. 돈과 권한 규칙을 외부 서비스 없이 테스트할 수 있게 나눈다.

### 구조

```
apps/web/app/api/            들어오는 쪽: 입력 검사 → 로그인 확인 → 유스케이스 호출
packages/core/src/
├─ domain/<영역>/            순수 규칙과 타입. 외부 패키지를 불러오지 않는다
├─ application/<영역>/       유스케이스와 포트(바깥 서비스용 인터페이스)
├─ adapters/out/             firestore/, livekit/, toss/, r2/
└─ container.ts              실제 어댑터를 연결한다
```

- 영역은 broadcast, chat, honey, donation, settlement, grade, moderation, recording으로 시작한다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 들어오는 쪽 | Next의 `app/api`(Route Handler)에 둔다. 유스케이스 하나만 부른다 | Next는 `app/` 안의 파일만 API 주소로 인식한다 |
| 파사드 | 두지 않는다 | 유스케이스가 이미 여러 일을 묶는다. 예를 들어 "방송 종료"는 LiveKit 방 닫기, 미션 꿀 돌려주기, 녹화 상태 바꾸기를 함께 한다(07 3장). 파사드를 두면 그대로 전달만 하는 파일이 늘어난다 |
| 포트 | 바깥 서비스 경계에만 둔다 | 규칙 테스트에 필요한 곳은 바깥 서비스 경계뿐이다 |
| 데이터 옮겨 담기 | 층마다 변환 객체를 만들지 않는다. zod로 검사한 타입을 그대로 넘긴다 | 1인 12일 일정에서 변환 코드는 버그만 늘린다 |
| 트랜잭션 | 트랜잭션 포트 `runInTransaction(tx => …)`를 하나 두고, 저장소 함수가 `tx`를 받는다 | 꿀이 움직이는 처리는 지갑, 꿀 내역, 충전, 후원을 한 번에 바꿔야 한다. Firestore 트랜잭션은 읽기를 모두 끝낸 뒤 써야 해서, 유스케이스도 이 순서를 지킨다 |
| 조립 | DI 라이브러리 없이 `container.ts`의 함수로 조립한다 | 연결할 어댑터가 네 종류뿐이다 |

### 테스트와의 관계

- 도메인 규칙(등급, 배분 비율, 꿀 먼저 쓰기, 제재 기간)은 외부 서비스 없이 단위 테스트한다.
- LiveKit과 토스는 가짜 어댑터로 바꿔서 유스케이스를 테스트할 수 있다.
- Firestore 저장소와 트랜잭션은 메모리 가짜로 테스트하지 않고 Firebase 에뮬레이터로 테스트한다. 가짜는 트랜잭션 동작이 실제와 달라서 버그를 놓친다.

### 위험

- 트랜잭션 포트 모양은 실제 유스케이스(예: 충전 확정)를 짜 보지 않고 정했다. 첫 유스케이스를 만들 때 다듬을 수 있다.

## 결정 18. API 약속은 zod로 정하고, OpenAPI 문서는 그 약속에서 만든다

- **결정일:** 2026-11-07
- **배경:** 백엔드와 프론트가 같은 레포에서 같은 TypeScript를 쓴다(결정 14). 그래서 API 명세 파일을 만들고 거기서 프론트 코드를 생성하는 단계(Swagger + orval)가 필요 없다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| API 약속 | `packages/shared/contracts/<영역>.ts`에 API마다 주소, 메서드, 요청 스키마, 응답 스키마를 zod로 적는다 | 화면과 서버가 같은 약속을 import한다. 응답 모양을 바꾸면 프론트에서 바로 타입 오류가 난다 |
| 서버 | `app/api`는 요청을 약속의 스키마로 검사하고, 응답도 약속의 스키마로 거른 뒤 보낸다 | 약속에 없는 값(익명 후원자의 실제 ID 등)이 실수로 브라우저에 나가지 않는다 |
| 프론트 | `src/shared/api`에 호출 함수 `apiFetch(약속, 입력)` 하나를 둔다. 로그인 토큰 붙이기와 오류 모양 통일을 맡는다. TanStack Query 훅은 FSD의 `entities`나 `features`의 `api` 폴더에 둔다 | 코드 생성 없이 타입이 맞는다 |
| API 문서 | 약속 목록을 읽어 `zod-openapi`의 `createDocument`로 OpenAPI 3.1 문서를 만드는 스크립트를 둔다. 문서를 보여주는 화면은 구현할 때 정한다 | 심사자와 README가 API를 한눈에 볼 수 있다. 약속과 문서가 어긋나지 않는다. zod 4의 `z.toJSONSchema`는 스키마 하나만 바꿔 줄 뿐 주소와 메서드가 담긴 문서는 만들지 않는다 |
| 약속 작성 규칙 | 날짜는 `z.date()` 대신 ISO 문자열(`z.iso.datetime()`)로 적는다. 약속 스키마에는 `transform`을 쓰지 않는다. Firestore 시각은 서버가 ISO 문자열로 바꿔서 보낸다 | `z.date()`와 `transform`은 JSON 스키마로 바꿀 수 없어서 문서를 만들 때 오류가 난다(zod 공식 문서) |
| BFF 서버 | 따로 두지 않는다. `app/api`가 이 웹만을 위한 API라서 이미 BFF 역할을 한다 | 화면 종류가 웹 하나뿐이고, 백엔드도 하나다. 중간 서버를 두면 전달만 하는 단계가 늘어난다 |
| 화면 단위 읽기 API | 화면 하나에 두 곳 이상의 데이터가 필요하면 그 화면용 읽기 API 하나로 묶어서 내려준다. 예: `GET /api/broadcasts/[id]/watch` | BFF의 장점을 서버를 늘리지 않고 가져온다. 쓰기 API는 유스케이스 단위로 둔다 |

### 뺀 후보와 이유

| 후보 | 뺀 이유 |
|---|---|
| Swagger 명세 + orval 코드 생성 | 같은 언어, 같은 레포라 생성 단계가 필요 없다. 명세 파일과 생성된 코드가 어긋날 곳만 는다 |
| ts-rest | 2026년 10월 26일에 저장소가 보관 처리되었고, 더 이상 유지보수하지 않는다고 공식 README에 적혀 있다. zod 4 지원도 정식판이 아닌 시험판(3.53.0-rc)에만 있다 |
| oRPC | 약속, 호출 함수, OpenAPI 문서를 한 번에 준다. 하지만 공식 문서가 다루는 v2가 아직 베타다. 라이브러리 작성 방식을 새로 익혀야 하고, 직접 만들 코드가 작다. 직접 만든 코드가 커지면 다시 검토한다 |

### 확인한 것 (2026-11-07, 공식 문서)

- zod 4의 `z.toJSONSchema`는 스키마 하나를 JSON 스키마로 바꾼다. 주소와 메서드가 담긴 OpenAPI 문서는 직접 조립하거나 라이브러리를 써야 한다. 출처: https://zod.dev/json-schema
- `zod-openapi` 6.x는 zod 4.0.0 이상만 지원하고, Node 22.14.0 이상이 필요하다. 출처: https://github.com/samchungy/zod-openapi
- ts-rest는 유지보수를 끝냈다. 출처: https://github.com/ts-rest/ts-rest
- oRPC 공식 문서는 v2 베타를 다룬다. 출처: https://orpc.dev

### 진행 순서

- 첫 API 2~3개(방송 만들기, 방송 보기, 충전 확정)를 만든 뒤 약속 형식과 `apiFetch`를 한 번 다듬는다.
- OpenAPI 문서 만들기는 필수 기능이 끝난 뒤에 붙인다. 약속 작성 규칙만 지키면 나중에 붙여도 고칠 것이 없다.

### 위험

- `zod-openapi` 때문에 Node 22.14.0 이상을 써야 한다. `.nvmrc`와 `engines`에 고정할 때(결정 10) 이 버전 이상으로 정한다.

| 홈의 방송 중 목록 | 방송 중인 예시 방송 4개를 채운다(2026-11-14 변경. 처음에는 채우지 않기로 했다). 영상은 나오지 않고, 홈 카드와 사이드바에 "예시" 표시를 붙인다. 방송 보기 화면은 "예시 방송이라 영상이 나오지 않아요"를 보여준다 | 심사자가 처음 들어왔을 때 빈 화면을 보지 않게 하려는 것이다. 영상이 없는 대신 "예시" 표시와 안내 문구로 가짜 방송임을 알린다. 직접 방송을 켜는 확인은 README 순서대로 그대로 할 수 있다 |
| 함께 쓰기 | 버튼 계정은 모든 심사자가 함께 쓴다 | README의 계정 정보와 확인용 명령이 늘 같아야 한다 |
| 초기화 | 부분 초기화(상태만 되돌림)와 전체 초기화(시드를 다시 만듦)를 둔다. 실제 사용자가 얽힌 돈 기록과 운영 기록은 지우지 않는다 | 다음 심사자가 처음 상태로 시작할 수 있다. 돈 기록과 운영 기록을 지우지 않는 원칙은 지킨다 |
| 샘플 계정 보호 | 샘플 계정도 제재와 정산 보류를 할 수 없다 | 샘플 계정이 막히면 다시보기와 다른 계정의 기록이 함께 사라진다 |

### 뺀 후보

| 후보 | 뺀 이유 |
|---|---|
| 심사자가 버튼을 누를 때마다 새 테스트 계정 만들기 | 심사자끼리 부딪히지 않는 장점이 있다. 하지만 README의 계정과 확인용 명령이 매번 달라진다. 방송자와 시청자 계정을 짝지어 주는 일도 생긴다 |
| 늘 켜져 있는 데모 방송(서버가 영상을 계속 송출) | LiveKit 무료 사용량을 하루 1,440분씩 쓴다(결정 6) |
| 시드 데이터를 Firestore에 직접 써 넣기 | 잔액과 내역, 등급과 후원 건수가 어긋나기 쉽다 |

### 위험

- **일정:** 시드 스크립트와 초기화는 기능이 거의 다 만들어진 뒤에야 완성된다. 실제 기능을 부르기 때문이다. 그래서 기능을 하나 만들 때마다 시드도 함께 늘린다.
- **실제 배포 데이터:** 배포 환경에 시드를 돌리면 실제 데이터와 섞인다. 시드 표시가 없는 문서는 건드리지 않고, 실행할 때 프로젝트 이름을 한 번 더 입력하게 해서 막는다.
- **확인하지 않은 것:** Firebase 사용자 지정 토큰을 Vercel 서버 함수에서 만드는 데 필요한 설정은 확인하지 않았다.


## 결정 22. 꿀은 나비가 파는 상품으로 보고, 환급·결제 한도·미성년자 규칙을 정한다

- **결정일:** 2026-11-07
- **배경:** 꿀은 돈을 먼저 받고 나중에 쓰게 하는 충전금이다. 2024년 9월부터 바뀐 전자금융거래법은 선불전자지급수단을 발행하는 회사에 등록을 요구한다. 또 충전금 전액을 신탁, 은행 예치, 지급보증보험 가운데 하나로 따로 맡기게 한다. 꿀이 여기에 해당하는지에 따라 할 일이 크게 달라진다. 그리고 지금 규칙에는 법에 걸릴 수 있는 부분이 있었다. 7일이 지나면 쓰지 않은 꿀도 돌려주지 않고, 탈퇴하면 남은 꿀이 사라진다. 결제 한도와 미성년자 규칙도 없었다.
- **이번 개발:** 공모 제출용으로 약관과 문서에 적는다. 실제 운영을 생각해서 로직도 만든다. 외부 계약이 필요한 본인인증과 송금만 목업으로 만든다(결정 11의 목업 원칙). 자세한 동작은 [07 기능 명세](07-feature-spec.md) 4-8, 4-11, 4-15에 있다.

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 꿀의 성격 | 꿀은 나비가 파는 후원용 디지털 상품이다. 후원에 쓴 꿀은 나비 매출이 된다. 방송자는 나비에게서 수익 배분금을 받는다(결정 9) | 지금 구조(충전할 때 부가세를 받고, 매출에서 방송자 몫을 나눠 줌)와 같다. 꿀을 나비 한 곳에서만 쓰므로 선불전자지급수단 규제를 피할 가능성이 크다. 해당하더라도 쓰는 곳이 1곳이면 등록이 면제된다 |
| 꿀을 옮기거나 바꾸는 기능 | 사용자끼리 꿀을 주고받는 기능과 꿀을 현금으로 바꾸는 기능은 만들지 않는다 | 이런 기능이 생기면 꿀이 돈처럼 움직인다. 그러면 상품으로 보기 어렵다 |
| 부르는 말 | 문서와 화면에서 "가상화폐"라고 쓰지 않는다. "포인트"라고 쓴다 | 가상자산법의 가상자산과 헷갈리지 않게 한다 |
| 미션 후원 | 미션 후원도 대가가 아닌 응원이다. 방송자는 미션을 수행할 의무가 없고 거절할 수 있다. 위험한 행동, 불법 행위, 선정적인 행동, 다른 사람을 괴롭히는 행동을 요구하는 미션은 금지한다 | 미션 후원은 "방송자의 행동에 값을 치르는 것"으로 보일 여지가 있다. 그러면 꿀이 제3자에게 대금을 치르는 수단이 된다. 대가가 아니라는 점을 약관과 안내 문구에 분명히 적는다 |
| 충전 취소(7일 안) | 지금처럼 충전하고 7일 안에 하나도 쓰지 않은 충전 건은 결제를 전액 취소한다 | 바꾸지 않는다 |
| 환급 신청 | 그 밖의 쓰지 않은 꿀은 사용자가 신청하면 돌려준다. 신청하면 꿀을 묶어 두고, 운영자가 확인한 뒤 본인 명의 계좌로 보낸다. 운영자가 거절하면 묶어 둔 꿀을 돌려준다 | 돈을 내고 산 잔액을 돌려주지 않으면 불공정 약관으로 볼 수 있다. 운영자가 확인하는 단계가 있어야 부정 결제를 걸러낼 수 있다 |
| 환급 수수료 | 결제 금액 기준으로 10%를 뗀다. 꿀 1개는 결제 금액 1.1원(부가세 포함)으로 계산한다. 원 단위 아래는 버린다. 예를 들어 3,000꿀이면 3,300원에서 10%를 떼고 2,970원을 보낸다 | 업계 관행이 10% 안쪽이다. 결제 수수료와 처리 비용을 메운다 |
| 환급할 수 있는 꿀 | 잔액에서 7일 안에 취소할 수 있는 충전 건의 꿀을 뺀 나머지 전부(결정 26에서 고침. 미션에 묶인 꿀은 이미 잔액에서 빠져 있다)다. 1,000꿀 미만이면 신청할 수 없다. 일부만 신청할 수는 없다 | 7일 안의 충전 건은 충전 취소로 전액을 돌려받는 편이 사용자에게 낫다. 일부 신청을 허용하면 계산과 화면이 복잡해진다 |
| 환급 계좌 | 본인인증한 이름과 예금주가 같은 계좌만 받는다. 은행 이름, 계좌번호 끝 4자리, 예금주만 저장한다 | 다른 사람 계좌로 돈을 빼돌리지 못하게 한다. 정산 정보(4-12)와 같은 저장 원칙이다 |
| 탈퇴 | 환급할 수 있는 꿀이 있으면 탈퇴 전에 환급 신청을 안내한다. 환급이 처리되는 중이면 탈퇴할 수 없다. 환급하지 않고 탈퇴하면 남은 꿀을 포기한다는 데 따로 동의를 받는다 | 남은 꿀이 말없이 사라지지 않게 한다 |
| 하루 충전 한도 | 한 계정이 하루에 충전할 수 있는 꿀은 100만 꿀(결제 금액 110만 원)이다. 하루는 한국 시간 0시부터 센다. "완료"된 충전과 만든 지 30분이 안 된 "결제 대기" 충전을 더해 센다 | 2018년 업계 자율규제와 2019년 방송통신위원회 가이드라인의 하루 100만 원 기준을 따른다. 결제 대기 건을 세지 않으면 결제창을 여러 개 열어 한도를 넘길 수 있다 |
| 후원 한도 | 한 번에 100만 꿀까지인 지금 규칙을 그대로 둔다. 하루 후원 합계는 따로 세지 않는다 | 충전을 막으면 후원도 자연히 막힌다 |
| 본인인증 | 처음 충전하기 전에 휴대폰 본인인증을 한 번 받는다. 이번에는 목업이다. 이름, 생년월일, 휴대폰 번호를 넣으면 인증된 것으로 처리한다 | 나이를 확인할 방법이 없으면 미성년자 규칙을 지킬 수 없다. 실제 본인인증은 인증 업체와 계약해야 한다 |
| 미성년자 | 만 19세 미만은 꿀을 충전할 수 없다. 시청, 채팅, 방송, 후원 받기는 지금처럼 할 수 있다 | 미성년자가 부모 동의 없이 결제하면 나중에 취소할 수 있다. 이미 방송자에게 나눠 준 돈도 나비가 돌려줘야 할 수 있다. 2019년 가이드라인은 부모 동의를 요구하는데, 성인만 충전하게 하면 그보다 엄격하다 |
| 같은 명의 후원 | 후원자와 방송자의 본인인증 명의가 같으면 그 후원에 "같은 명의" 표시를 남긴다. 운영자 화면의 회원 상세와 정산 관리에 보여준다. 운영자는 지금 있는 "정산 보류"로 처리한다 | 방송자가 다른 계정으로 카드 결제를 해서 자기 방송에 후원하면 카드 결제가 정산금(현금)으로 바뀐다. 이것은 카드깡(카드로 현금을 만드는 것)이고 법 위반이 될 수 있다 |
| 현금영수증 | 계좌이체처럼 현금으로 결제하면 충전할 때 현금영수증을 발급한다. 토스페이먼츠 결제창의 현금영수증 기능을 쓴다. 충전을 취소하면 현금영수증도 취소한다. 카드 결제는 카드 전표가 증빙이라 발급하지 않는다 | 충전할 때 부가세를 받고 있으므로 충전 시점에 발급하는 것이 맞다. 결제대행사 기능이 있어 직접 만들 필요가 없다 |
| 회계(실제 운영 시) | 충전하면 받은 돈을 선수금(아직 서비스를 주지 않은 돈)과 부가세 예수금으로 나눈다. 후원이 확정되면 선수금을 매출로 바꾼다. 미션에 묶인 꿀은 확정되기 전까지 매출이 아니다. 5년 동안 쓰지 않아 사라진 꿀은 그때 수익으로 잡는다 | 공모에서는 테스트 결제라 장부를 만들지 않는다. 문서에만 적는다 |

### 실제로 만드는 것과 목업

| 실제로 만든다 | 목업으로 만든다 |
|---|---|
| 하루 충전 한도 확인, 만 19세 미만 충전 거절, 환급할 수 있는 꿀과 환급 금액 계산, 환급 신청과 꿀 묶기, 운영자의 승인과 거절, 같은 명의 표시, 탈퇴 안내 | 휴대폰 본인인증, 환급 계좌 확인, 환급 송금(정산 송금 목업과 같은 함수를 쓴다) |

- **순서:** 하루 한도와 나이 확인은 충전 기능과 함께 만든다. 충전 주문을 만드는 곳에 확인 두 개를 더하는 정도다. 환급 신청과 운영자 처리는 필수 기능이 끝난 뒤 정산 목업과 함께 만든다. 일정이 모자라면 환급 화면을 빼고 약관과 안내 문구만 남긴다.

### 뺀 후보와 이유

| 후보 | 뺀 이유 |
|---|---|
| 꿀을 "방송자에게 보내는 돈"으로 보기 | 제3자에게 대금을 치르는 수단이 되어 선불업 등록과 충전금 전액 신탁이 필요할 수 있다. 지금 구조와도 맞지 않는다 |
| 부모 동의를 받고 미성년자도 충전하게 하기 | 부모 인증 화면, 동의 기록, 월 한도 계산이 늘어난다. 결제 취소 위험도 완전히 없어지지 않는다 |
| 환급 수수료 없음 | 결제 수수료를 나비가 모두 부담한다. 업계 관행(10% 안쪽)을 넘는 혜택이다 |
| 결제를 남은 금액만큼 부분 취소해서 환급하기 | 카드사마다 취소 기한이 있어서 오래된 충전은 돌려줄 수 없다. 결제 수단마다 처리 방법도 달라진다 |
| 하루 후원 합계 따로 세기 | 충전 한도로 충분하다 |

### 위험

- **법 해석:** 별풍선 같은 후원 아이템이 선불전자지급수단인지에 대한 금융위원회의 공식 판단을 찾지 못했다. 실제로 운영하기 전에 금융위원회에 묻거나 변호사 의견을 받아야 한다.
- **미션 후원:** 약관에 "대가가 아니다"라고 적어도, 실제로는 대가로 볼 수 있다는 해석이 남는다.
- **한도 우회:** 한도는 계정 단위로 센다. 한 사람이 계정을 여러 개 만들면 넘길 수 있다. 실제 운영에서는 본인인증 명의 단위로 세는 것이 맞다. 이번에는 계정 단위로 둔다.
- **일정:** 본인인증 목업 화면, 환급 신청 화면, 운영자 환급 화면이 새로 생긴다.
- **확인하지 않은 것:** 통신판매업이 현금영수증 의무발행업종인지, 등록이 면제된 선불업자에게도 충전금 별도관리 의무가 있는지, 매출을 후원 총액으로 잡을지 나비 몫만 잡을지는 세무사와 변호사 확인이 필요하다. 토스페이먼츠 테스트 모드에서 현금영수증 발급까지 해 볼 수 있는지도 확인하지 않았다. 한도 규제를 법으로 만든 개정안이 통과됐는지도 확인하지 못했다.

## 결정 24. 방송 중에는 지울 수 없고, 녹화는 방송을 시작할 때 고른다

- **결정일:** 2026-11-07
- **배경:** 와이어프레임 J-5는 방송 중인 방송을 내 방송 관리에서 "종료하고 삭제"할 수 있게 그렸다. 하지만 방송 중인 방송을 목록에서 지우는 흐름은 이상하다. 녹화는 방송이 끝나야 올라온다. 그래서 방송이 끝나야 관리 목록에서 다루는 것이 맞다. 녹화 여부도 방송 만들기가 아니라 방송을 켜는 순간에 정하는 것이 자연스럽다.
- **이번 개발:** 자세한 동작은 [07 기능 명세](07-feature-spec.md) 3장, 4-3, 4-4, 4-5, 4-9, 4-10에 있다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 방송 중 삭제 | 할 수 없다. 화면에 삭제 버튼이 없고, 서버도 거절한다 | 사용자 결정이다. 방송을 끝낸 뒤에 지운다 |
| 내 방송 관리 목록 | 종료된 방송만 보여준다. 준비 상태와 방송 중인 방송은 목록 위의 "지금 방송" 카드로 따로 보여주고, 카드에서 송출 화면으로 들어간다 | 사용자 결정이다. 녹화와 후원 내역은 방송이 끝나야 정리된다 |
| 준비 상태 방송 삭제 | 카드에서 지울 수 있다 | 아직 송출하지 않아서 남는 녹화가 없다 |
| 녹화 고르는 때 | 송출 화면에서 "방송 시작" 바로 위의 "이 방송 녹화하기" 스위치로 고른다. 기본은 꺼짐이다. 방송이 시작되면 바꿀 수 없다 | 사용자 결정이다. 방송 만들기에서는 녹화를 고르지 않는다 |
| 방송을 끝내는 경로 | 종료 버튼, 크롬 공유 중지, LiveKit 끊김 알림, 운영자의 강제 종료와 방송 금지다. "방송 중 삭제"는 경로에서 뺀다 | 방송 중에는 삭제할 수 없기 때문이다 |

### 바뀐 것

- 결정 7의 "녹화 중인 방송 삭제: 녹화 중이거나 처리 중이면 지울 수 없다"는 "방송 중이면 지울 수 없고, 녹화가 처리 중이면 지울 수 없다"로 바뀐다.
- 피그마 J-5(방송 삭제 확인 · 방송 중)는 지운다. J-1, J-2의 목록에서 방송 중인 줄을 빼고, 위쪽에 지금 방송 카드를 그린다. C-3(녹화 켬)의 녹화 스위치는 D-5(PC 미리보기)와 F-4(휴대폰 미리보기)로 옮긴다.

| 방송과 송출 | 시청 권한은 준비와 방송 중일 때만 준다. 송출자가 나갔다는 알림이 와도 같은 이름으로 방에 있으면 종료하지 않는다. 녹화가 "처리 중"으로 30분 지나면 실패로 바꾼다. 녹화는 한 번에 3분, 한 달 합계 50분까지다 |
| 공통 저장 | 브라우저가 정한 번호를 문서 ID로 쓰는 문서는 `create`로만 저장한다. 작성자가 다르면 409다. 후원의 정산 ID는 처음부터 null로 넣는다. 빠진 색인 7개를 결정 19의 색인 목록에 더했다 |
| 채팅 | 채팅 문서에 작성자 등급, 미션 내용, 미션 상태, 마감 시각을 넣는다. 금칙어 변경은 1분 안에 적용된다 |
| 후원과 꿀 | LiveKit으로 보내는 후원 항목도 익명이면 후원자 ID를 뺀다. 모자란 꿀이 10만 꿀을 넘으면 1,000 단위로 올려 충전한다. 거절·취소된 미션은 확정 시각을 비운다. 미션 성공 때 마감 시각을 다시 확인한다 |
| 운영자 | 신고는 대상 사용자별로 묶는다. 익명 후원 항목에는 "이 메시지 신고"만 둔다. 테스트 운영자는 시드 계정 안에서만 검색한다. 안내 문구는 "테스트 운영자는 심사용 계정만 보고 조치할 수 있어요" 하나로 쓴다. 대시보드의 무료 한도 사용량은 우리 기록으로 계산한 녹화·방송 시간과 각 서비스 관리 화면 링크로 바꾼다 |
| 정산 | 정산 기록 ID 끝에 순번을 붙인다. 새 후원이 없어도 지급 단계는 실행한다. 영구 정지 방송자의 새 정산 기록은 처음부터 "보류(운영 조치)"다. 탈퇴할 때 받지 못한 수익 배분금이 있으면 기다릴지 포기할지 고르게 하고, 포기하면 "포기" 상태로 남긴다 |
| 시드와 초기화 | 시드 스크립트는 "시드 실행자"로만 테스트 계정 보호를 건너뛴다. 꿀을 늘릴 때는 승인 시각이 10일 전인 시드 충전을 만든다. 승급 직전으로 되돌릴 때만 등급과 횟수를 직접 덮어쓴다. 테스트 시청자의 하루 한도는 마지막 부분 초기화부터 다시 센다. 전체 초기화는 시드 계정이 주인인 문서를 모두 지운다. 제재 연습용 계정에 받은 후원과 정산 계좌를 넣어 정산 보류를 시연한다 |
| 공개 테스트 계정 | 버튼 로그인은 같은 IP에서 1시간에 20번까지다. 테스트 방송자의 방송은 30분까지다. 심사가 끝나면 버튼 로그인을 끈다 |
| 문서와 피그마 | 개인정보 수집 항목에 본인인증 정보와 계좌를 더한다. 피그마 화면의 단위, 문구, 예시 숫자, 컴포넌트 이름, 레이어 이름을 문서에 맞춘다 |

### 위험

- 3분, 50분, 30분, 20번은 임시값이다.
- 테스트 방송자의 30분 제한은 송출 화면과 서버가 함께 지킨다. 송출 화면을 일부러 고친 사람은 서버 확인 때까지 더 방송할 수 있다.


## 결정 28. 개발 방식을 정하고 3차 전수조사의 빈틈을 메운다

- **결정일:** 2026-11-07
- **배경:** 3차 전수조사에서 사용자가 정해야 할 것 세 가지와 문서 빈틈이 나왔다. 사용자는 스펙을 줄이지 않고 빈틈을 고쳐서 진행하기로 했다. 코딩은 Claude가 맡고, 사용자는 반복 실행(루프)으로 개발을 돌린다.

### 개발 방식

| 항목 | 결정 | 이유 |
|---|---|---|
| 스펙 | 줄이지 않는다. 빼는 순서 표는 일정이 정말 모자랄 때만 쓴다 | 사용자 결정이다. 코딩은 Claude가 하므로 일정 여유가 있다고 본다 |
| LiveKit 사용 | 개발 중 송출 테스트는 내 컴퓨터의 LiveKit 개발 서버(`livekit-server --dev`)로 한다. 클라우드 LiveKit은 배포 점검처럼 꼭 필요한 경우에만 짧게 쓴다. 클라우드 송출 테스트는 사용자가 수동으로 한다 | 개발과 심사가 같은 달의 무료 한도(참가자 5,000분, 녹화 60분)를 쓴다. 개발에서 다 쓰면 심사 중에 송출이 실패한다 |
| 토스페이먼츠 | 사업자 없이 테스트 키로 연동한다. 목업 결제 대안은 두지 않는다 | 사용자가 확인했다. 공모는 테스트 결제만 요구한다 |
| 실제 기기 테스트 | 개발이 끝난 뒤 사용자가 직접 한다(맥북 크롬 탭 소리, 아이폰 카메라, 휴대폰 데이터 시청) | 사용자 결정이다. 결과에 따라 송출 쪽 코드를 고칠 수 있다 |

### 메운 빈틈

| 영역 | 결정 |
|---|---|
| 전체 초기화 | 먼저 시드 계정의 준비·방송 중 방송을 종료 함수로 끝낸다. 진행 중인 미션, 결제 대기·취소 중 충전, 처리 중 환급, 송금 중 정산이 있으면 거절한다. 실제 사용자가 걸린 후원 기록은 지우지 않고 시드 쪽 이름만 바꾼다. 시드 방송자의 정산 기록은 결정 27대로 모두 지우고, 그 안의 실제 사용자 후원은 정산 ID를 null로 되돌린다 |
| 시드 실행자 | 운영자 화면의 초기화 API만 예외로, 대상이 시드 계정일 때 서버 안에서 시드 실행자를 쓴다. 시드의 지난 방송은 시드 실행자가 "종료" 상태로 바로 만들고, 횟수·시간·등급도 직접 쓴다 |
| 부분 초기화 | 신고 4건은 시드가 만든 문서를 "접수"로 덮어쓴다. 테스트 시청자에게 걸린 활동 제한을 지운다. 제재 연습용 계정의 제재를 모두 풀고 정지도 푼다. 정지 예시 계정은 영구 정지를 다시 건다 |
| 정산 보류 | 보류는 방송자 단위로 건다. 걸면 그 방송자의 대기 기록과 새 기록이 모두 "보류(운영 조치)"가 된다. 테스트 실행 결과 문구에 보류로 남은 기록 수를 보여준다 |
| 운영자 가림 | 테스트 운영자에게는 운영자 화면의 모든 목록에서 실제 사용자 줄을 가린다. 운영 기록, 제재 관리, 이의 제기도 들어간다 |
| 탈퇴 | 결제 대기·취소 중 충전이 있으면 탈퇴할 수 없다. 남은 꿀을 포기하면 꿀 내역에 "탈퇴 포기" 줄을 남긴다 |
| 환급 | "송금 실패"인 신청도 다시 승인하거나 거절할 수 있다 |
| 녹화 사용량 | 녹화 기록과 따로 `usage` 문서에 센다. 시작할 때 3분을 미리 더하고, 지워도 줄지 않는다. 서버도 3분이 지났는지 확인해 멈춘다 |
| 익명 후원 | 채팅 모음의 익명 후원 항목은 등급과 방송자 여부도 비운다. 내 신고 내역에는 "익명 후원 메시지"로만 보여준다 |
| 알림 | 미션 상금과 응원금이 확정되면 방송자에게도 알린다. 그래서 시드의 후원 받음 알림 6건이 맞는다 |
| 필드와 색인 | 사용자 문서에 마지막 부분 초기화 시각과 정산 보류를, 충전에 취소 요청 시각을, 후원에 포기 여부를 더했다. 시드 상태, 요청 횟수, 사용량 문서를 새로 두었다. 색인 3개를 결정 19 목록에 더했다 |
| 그 밖 | 다시보기 서명 주소는 30분 동안 쓸 수 있다. 정산 카드는 실제 지급일 날짜로 이름을 붙인다. 심사 시나리오 10-6의 12번 전에 부분 초기화를 한다. 결정 16의 폴더 위치를 `apps/web`로 고쳤다 |

### 위험

- 개발 서버와 클라우드 LiveKit의 동작이 조금 다를 수 있다. 클라우드에서만 생기는 문제는 사용자가 수동 테스트로 찾는다.
- 실제 기기 테스트를 개발 뒤로 미뤘다. 탭 소리나 아이폰 카메라가 예상과 다르면 송출 쪽 코드를 다시 고쳐야 한다.


## 결정 29. 정책과 기획이 부딪히는 곳을 맞춘다

- **결정일:** 2026-11-07
- **배경:** 정책(약관, 안내 문구, 운영 규칙)과 기획(약속, 실제 동작)을 대조했다. 약관이 실제 동작보다 좁거나, 사용자에게 불리한 규칙이 약관에 없거나, 정책끼리 부딪히는 곳이 나왔다.
- **문서:** [09 방송자 이용약관](09-streamer-terms-draft.md)을 고쳤다. 모든 회원에게 적용되는 [10 이용약관 초안](10-terms-of-service-draft.md)을 새로 만들었다. 기능은 [07 기능 명세](07-feature-spec.md)에 "(06 결정 29)"로 표시했다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 정산 보류 범위 | 기능은 그대로 방송자 단위로 정산 전체를 보류한다. 약관을 "정산 전체를 보류할 수 있다"로 바꾸고, 영구 정지를 보류 사유에 넣고, 언제 푸는지 적었다 | 약관이 "관련된 금액만큼"이라고 해서 기능보다 좁았다 |
| 시청자 꿀 규칙 동의 | 모든 충전 창에 "꿀 충전과 후원 유의사항에 동의합니다"와 "안내 보기"를 둔다. 동의한 안내 버전과 시각을 충전 기록에 저장한다. 꿀 규칙 전문은 10 이용약관 제3조~제5조다 | 내 꿀 화면에서 충전하는 사람은 환급 수수료와 꿀 포기 규칙을 보지 않고 결제했다 |
| 다시보기 약속 | 00·04의 약속을 "녹화를 켜면 짧은 다시보기(한 번에 3분까지)가 남는다"로 바꿨다. 녹화 스위치 도움말에 3분 제한을 적는다. 등급별 보관 기간은 "추후 적용"으로 표시한다 | 녹화는 무료 한도 때문에 3분과 월 50분으로 제한한다(결정 27). 약속이 실제보다 컸다 |
| 제재 중 탈퇴 | 채팅 금지나 방송 금지가 적용 중이면 탈퇴할 수 없다 | 탈퇴하고 다시 가입해서 제재를 피할 수 있었다 |
| 운영 조치 알림 | 채팅 숨김, 방송 강제 종료, 다시보기 비공개를 당사자에게 알린다. 운영자는 종료된 방송의 다시보기를 비공개로 바꿀 수 있다. 약관에 제재 4단계, 이의 제기, 영구 정지 때의 계약 종료를 적었다 | 약관은 알린다고 약속했는데 기능이 없었다 |
| 꿀 안내 문장 | "현금으로 바꿀 수 없다"를 "다른 사람에게 넘길 수 없다. 쓰지 않은 꿀은 환급 신청으로 돌려받는다"로 바꿨다 | 같은 안내 창에서 환급 문장과 반대로 읽혔다 |
| 같은 명의 후원 | 승급에 필요한 받은 후원 건수에서 뺀다 | 자기 후원으로 등급을 올릴 수 있었다. 방송자가 충전한 적이 없으면 같은 명의를 찾지 못하는 한계는 남는다 |
| 테스트 계정 보호 | 테스트 운영자에게만 적용한다. 실제 운영자는 테스트 계정도 제재할 수 있고, 부분 초기화가 그 제재를 풀어 준다 | 비밀번호 없이 누구나 들어오는 계정으로 나쁜 방송을 해도 막을 수 없었다 |
| 공모 기간의 정산 | 방송자 약관 부칙에 "공모 기간 결제와 정산은 시연용이고, 심사용이 아닌 방송자는 수익 배분금을 받을 수 없다"를 적었다 | 정산 정보 등록 화면이 없다 |
| 알 수 없던 정책 | 녹화 제한, 기록 보관 기간, 운영 기록 보관, 방송 금지 안내 공개, 채팅 금지와 후원 메시지, 탈퇴할 수 없는 경우 전체, 결제 대기의 한도 포함, 응원금 100꿀 버림을 약관과 안내 문구에 적었다 | 사용자에게 불리한 규칙은 약관이나 안내에 있어야 한다 |
| 약속 문구 | 03·04에 남은 "충전 없이 바로 후원"을 결정 8에 맞췄다. 만 19세 미만은 꿀로 후원할 수 없다는 점을 00·04에 적었다. 04의 "수익 배분은 설명만 한다"를 00에 맞춰 "보여줄 수 있다"로 고쳤다 | 앞선 결정이 바꾼 약속이 남아 있었다 |

### 위험

- 약관 두 개는 법률 검토를 받지 않은 초안이다.
- 방송자가 충전한 적이 없으면 같은 명의 후원을 찾지 못한다. 정산 정보 등록 때 본인인증을 하게 하면 풀리지만, 이번에는 등록 화면이 없다.


## 결정 30. 방송 종료 규칙의 빈틈을 메운다

- **결정일:** 2026-11-08
- **배경:** 개발 착수 전 전수조사에서 "방송은 어떤 방법으로 끝나도 반드시 종료된다"는 조건에 빈틈 5개가 나왔다. 송출 코드를 쓰기 전에 정해야 하는 것들이다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 방송 중 송출 화면 다시 들어가기 | 막는다. 송출용 접속 권한은 준비 상태인 방송에만 준다. 방송 중에 송출 탭을 새로고침하거나 닫으면 방송이 끝난다. 송출 화면은 나가기 전에 브라우저 기본 확인 창을 띄운다. 내 방송 관리의 방송 중 카드에서 "송출 화면 열기"를 뺀다 | 테스트 방송자 계정은 심사자가 함께 쓴다. 다시 들어가기를 허용하면 다른 심사자가 진행 중인 방송을 가로챌 수 있다. "끊기면 끝난다" 원칙과도 맞는다 |
| 네트워크가 흔들릴 때 | 막지 않는다. LiveKit이 스스로 다시 연결할 때는 처음 받은 권한을 쓰므로 우리 서버를 거치지 않는다 | 다시 들어가기를 막아도 잠깐 끊긴 방송은 이어진다. 그래서 서버가 "나갔다" 알림 뒤에 따로 기다릴 필요가 없다 |
| LiveKit 방 이름 | 방송 ID와 같게 한다 | 웹훅이 방 이름으로 방송 문서를 바로 찾는다. 따로 이어 주는 표가 필요 없다 |
| 시작 실패(30초) | 송출 화면이 LiveKit 연결을 끊는다. 다시 시도하면 새 권한을 받는다 | 연결이 남아 있으면 늦게 올라온 영상 때문에 화면은 실패인데 방송은 켜지는 일이 생긴다. 연결을 끊으면 늦게 온 알림은 송출자가 방에 없어서 무시된다 |
| 휴대폰에서 돌아왔을 때 | 송출 화면이 서버의 방송 상태를 확인한다. 종료면 "방송이 끝났어요"를 보여준다. 방송 중이고 다시 연결됐으면 송출 화면을 그대로 둔다. 방송 중인데 연결되지 않았으면 종료를 요청한다 | 다시 연결에 성공했는데 화면만 "끝났어요"를 보여주는 일을 막는다 |
| 준비 상태 방송 삭제 | LiveKit 방도 닫는다. 방이 없으면 오류로 보지 않는다 | 준비 상태에서도 시청자가 방에서 기다린다. 방을 닫지 않으면 무료 사용량이 계속 줄어든다 |
| 권한 표 | "송출 시작"과 "송출 확인"은 준비 상태만 허용한다. "방송 종료"는 방송 중만 허용한다. "녹화 멈춤"은 소유자가 방송 중이고 녹화 중일 때만 허용한다. "미션 마감 처리 요청"은 누구나 할 수 있고 서버가 마감 시각을 확인한다 | 권한 표에 상태 조건과 요청 세 개가 빠져 있었다 |

### 뺀 후보

- **허용하고 앞 연결을 끊는다:** 새로고침해도 방송이 이어진다. 하지만 공용 테스트 계정에서 가로채기가 생긴다. 서버가 "나갔다" 알림 뒤에 몇 초 기다리는 규칙도 새로 필요하다.
- **같은 브라우저만 허용한다:** 방송을 시작할 때 서버가 만든 값을 브라우저에 저장하고, 그 값이 있는 브라우저에만 권한을 다시 준다. 실제 서비스에는 가장 좋다. 하지만 필드와 비교 로직, 기다리는 시간 규칙이 더 필요하다. 기획서에 다음 단계로 적는다.

### 위험

- LiveKit이 스스로 다시 연결할 때 처음 받은 권한을 쓴다는 것과 같은 이름으로 다시 들어오면 앞 연결이 끊긴다는 것은 실제로 해 보지 않았다. 첫 배포 뒤에 확인한다.
- PC에서 실수로 새로고침하면 방송이 끝난다. 확인 창으로 줄이지만 없애지는 못한다.


## 결정 31. 홈을 콘텐츠로 채우고, 카테고리와 시청자 수를 만든다

- **결정일:** 2026-11-14
- **배경:** 나비는 콘텐츠 노출이 핵심인 방송 사이트다. 심사자가 처음 들어왔을 때 홈이 비어 보이면 서비스가 작동하지 않는 것처럼 보인다. 치지직 첫 화면과 견주면 안내 카드, 대표 방송, 광고 자리, 카테고리, 다시보기가 없어 특히 비어 보였다. 구성과 밀도만 참고하고 그림, 로고, 문구는 가져오지 않는다.
- **문서:** [07 기능 명세](07-feature-spec.md)의 4-2, 4-3, 4-6, 4-16, 9장에 "(06 결정 31)"로 표시했다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 홈 구성 | 안내 카드 줄, 대표 방송 1개와 작은 방송 4개, 가로 광고 배너("광고 예시"), 카테고리별 방송 줄, 다시보기 줄, 오른쪽 아래 이벤트 팝업 | 방송이 몇 개 없어도 화면이 채워지고, 방송이 없을 때도 방송 영역만 비고 나머지는 보인다 |
| 광고 | 실제 광고는 붙이지 않고 "광고 예시" 배너로 자리만 보여준다. 도움말로 광고가 나비의 수익 모델이라고 알린다 | 수익 구조 설명은 만들고(07 9장), 광고 연동은 만들지 않는다 |
| 사이드바 | PC에서는 왼쪽에 붙은 영역으로 열고 닫고, 고른 상태를 브라우저에 저장한다. 처음에는 열림. 휴대폰은 덮는 방식 그대로 | 열었을 때 콘텐츠를 어둡게 덮으면 방송 목록을 보며 메뉴를 쓸 수 없다 |
| 카테고리 | 잡담, 게임, 공부, 음악, 요리, 그림, 운동, 여행 8개 고정. 방송 문서의 `category`에 저장하고 없으면 "잡담". 방송 만들기에서 고른다(필수 아님) | 방송을 주제별로 보여주면 같은 방송 수로도 홈이 더 풍성하다. 시청자 수 정렬이 아니므로 작은 방송 발견 원칙(결정 5)은 그대로다 |
| 시청자 수 | 웹훅의 시청자 입장·퇴장 때마다 LiveKit 참가자 목록에서 `viewer_` 이름 수를 다시 세어 방송 문서 `viewerCount`에 저장한다. 종료하면 0. 홈 카드, 사이드바, 방송 보기에 "N명"으로 보여준다 | 하나씩 더하고 빼면 알림이 빠질 때 숫자가 틀어진다. 매번 다시 세면 다음 알림에서 바로잡힌다. 이전 명세는 요구사항에 없어서 뺐지만, 방송이 살아 있다는 느낌을 주려고 넣는다. 정렬 기준으로는 쓰지 않는다 |

### 위험

- 한 사람이 탭을 여러 개 열면 여러 명으로 센다.
- 웹훅이 늦거나 빠지면 다음 입장·퇴장 알림이 올 때까지 숫자가 어긋나 있다.
- 시드 방송의 카테고리와 시청자 수는 시드 쪽에서 채워야 홈 섹션이 차 보인다.

## 결정 32. 채팅 수정과 삭제를 만든다

- **결정일:** 2026-11-19
