## 1. 무엇을 만드는가

나비는 프로그램 설치도 구독자 조건도 없이 브라우저에서 바로 켜는 방송 플랫폼이다.

- 방송자는 버튼 하나로 화면과 소리를 내보낸다.
- 시청자는 링크를 열면 가입 없이 바로 본다.
- 방송이 끝나면 채팅과 후원 내역이 남고, 녹화를 켰다면 짧은 다시보기(한 번에 3분까지)가 남는다. 남은 반응이 다음 방송을 켤 이유가 된다.

## 2. 왜 필요한가

- 치지직은 사이트 안에 방송 시작 버튼이 없다. 외부 송출 프로그램(OBS, PRISM)을 설치하고 스트림 키를 붙여 넣어야 방송할 수 있다.
- 이 준비 단계가 길어서 보여주고 싶은 순간이 방송으로 이어지지 않는다.
- 함께 지킬 조건이 하나 있다. 방송은 어떤 방법으로 끝나도 확실하게 종료 상태가 되어야 한다. 종료 버튼, 크롬의 공유 중지, 휴대폰 화면 잠금이 모두 해당한다.

## 3. 누구를 위한가

| 사용자 | 원하는 것 | 나비가 약속하는 것 |
|---|---|---|
| 가볍게 한 번 보여주는 사람 | 바로 켜고, 링크로 나누고, 확실하게 끈다 | 설치 없이 켠다. 디스코드와 달리 초대 없이 누구나 본다. 끝난 뒤에도 기록이 남는다 |
| 입문 스트리머 | 장비 없이 첫 방송을 켜고, 끝나면 기록과 반응과 수익이 남는다 | 치지직과 달리 송출 프로그램이 필요 없다. 끝나면 다시보기와 후원 내역이 남는다 |
| 시청자 | 가입 없이 바로 보고, 필요할 때만 로그인한다 | 가입 없이 본다. 꿀이 모자라도 "충전하고 후원하기" 한 번으로 후원한다(06 결정 8). 꿀 충전은 만 19세 이상만 할 수 있다(06 결정 22) |

가볍게 켠 사람이 반응과 후원을 받으면 다시 켠다. 그렇게 다시 켜는 사람이 입문 스트리머가 된다. 나비는 이 흐름을 기본 이야기로 삼는다.

## 4. 시장에서의 위치

- **차별점:** 치지직, SOOP, 유튜브, 인스타그램은 모두 PC 방송에 외부 프로그램이 필요하다. 휴대폰 방송은 유튜브가 구독자 50명, 틱톡이 팔로워 1,000명을 요구한다. 틱톡 조건은 확인이 필요하다.
- **간접 경쟁:** StreamYard는 브라우저에서 송출한다. 하지만 플랫폼이 아니라서 시청자, 후원, 다시보기를 직접 주지 않는다.
- **약점:** 나비에는 시청자가 없다. 브라우저 송출은 큰 플랫폼도 쉽게 따라 할 수 있다.
- **피할 것:** 시청자 수, e스포츠 중계, 대형 방송자 영입으로 경쟁하지 않는다.

## 5. 어디서 막히는가

브라우저 송출로 큰 단계 두 개(프로그램 설치, 스트림 키)는 사라진다. 대신 작은 단계에서 사용자가 막힌다. 막히는 지점 상위 다섯 개는 다음과 같다.

1. 탭 오디오 공유 체크를 놓쳐서 소리 없는 방송이 나간다.
2. 크롬 공유 창에서 탭, 창, 전체 화면 중 무엇을 고를지 모른다. 전체 화면을 고르면 맥 화면 기록 권한과 크롬 재시작이 필요하다.
3. 휴대폰에서 링크를 보내려고 메신저로 넘어가면 카메라가 끊긴다.
4. 한 번만 쓰려는 사람에게도 가입과 로그인을 요구한다.
5. 권한 창에서 거부하면 다시 켜는 방법을 모른다.

시청자도 막힌다. 아이폰에서는 영상이 소리가 꺼진 채 재생된다. 그래서 시청자는 방송이 고장 났다고 생각할 수 있다.

| 구분 | 할 일 |
|---|---|
| 화면 안내로 바로 할 수 있는 것 | 공유 창과 권한 창이 뜨기 전에 안내한다. 방송 제목에 기본값을 넣는다. 시청 화면에 "눌러서 소리 켜기" 버튼을 크게 둔다. 종료 화면에서 다시보기와 후원 내역으로 연결한다 |
| 개발이 더 필요한 것 | 송출과 방송 상태를 하나로 묶는다. 탭 소리와 마이크 소리를 따로 보여주는 소리 확인 막대를 만든다. 로그인한 뒤 하던 화면으로 돌아오게 한다 |

공모 요강은 README에 테스트 계정이나 테스트 계정으로 바로 로그인하는 기능을 요구한다. 이 기능은 심사자가 가입 단계 없이 바로 방송을 켜게 해 준다. 그래서 켜기 장벽을 줄이는 설계에도 포함한다.

## 6. 수익 구조

| 수익 | 방식 | 이번 개발 |
|---|---|---|
| 후원 수수료 | 방송자가 등급에 따라 후원의 80~88%를 받고, 나비가 나머지 12~20%를 받는다 | 만들었다. 토스페이먼츠 테스트 모드로 결제한다 |
| 광고 | 방송에 들어갈 때 2번에 1번꼴로 보여준다. 5초 뒤에 건너뛸 수 있다. 처음 들어온 시청자에게는 보여주지 않는다. 같은 시청자에게는 30분에 1번, 하루 6번까지만 보여준다. 방송자가 광고 수익의 60%를 받는다. 자세한 규칙은 결정 32에 있다 | 홈에 "광고 예시" 배너로 자리만 보여준다. 실제 광고는 붙이지 않았다 |
| 채널 구독 | 그 채널에서 광고가 나오지 않는다. 방송자가 구독료의 80%를 받는다 | 설명만 한다 |
| 플랫폼 구독 | 모든 방송에서 광고가 나오지 않는다 | 설명만 한다 |

네 가지 수익은 모두 시청자에게서 나온다. 초기에는 시청자가 적어서 수익 대부분이 후원 수수료에서 나올 것으로 추론한다.

### 후원 수익이 움직이는 방식

| 단계 | 규칙 | 근거 |
|---|---|---|
| 꿀 충전 | 시청자가 꿀(후원용 포인트)을 산다. 꿀 1개는 1원이고 부가세 10%를 더해 결제한다. 예를 들어 5,000꿀은 5,500원이다 | 06 결정 8, 22 |
| 충전 조건 | 본인인증을 한 만 19세 이상만 충전한다. 한 계정이 하루에 충전할 수 있는 꿀은 100만 꿀이다 | 06 결정 22 |
| 후원 | 시청자가 꿀로 방송자에게 후원한다. 채팅 후원과 미션 후원이 있다 | 06 결정 8 |
| 수익 배분 | 등급별로 방송자 몫이 다르다. 알 80%, 애벌레 82%, 번데기 85%, 나비 88%다. 모든 등급이 치지직의 같은 단계(60~80%)보다 많다 | 06 결정 3, 9 |
| 정산 | 월 1회 자동으로 정산한다. 방송자는 조회만 한다. 송금은 목업이다 | 06 결정 9, 11 |
| 충전 취소 | 충전하고 7일 안에 하나도 쓰지 않은 충전은 전액 취소한다 | 06 결정 8 |
| 환급 | 그 밖의 쓰지 않은 꿀은 신청하면 결제 금액에서 10%를 떼고 본인 계좌로 돌려준다. 1,000꿀 미만은 신청할 수 없다 | 06 결정 22 |

나비 몫은 후원의 12~20%다. 여기서 카드 결제 수수료(약 3%로 추정)를 낸다. 최상위 등급에서도 나비에게 약 9%가 남는다.

## 7. 개발 범위

- **공모 필수와 선택 항목:** PC 방송(탭 공유, 탭 소리, 마이크), 모바일 웹 카메라 방송, 방송 등록·수정·삭제·목록·시청, 인증과 소유자 권한, 채팅, 후원, 녹화와 다시보기를 모두 만들었다.
- **공모 요강 밖에서 더 만든 것:** PC 방송에서 화면과 카메라 함께 보내기, 구글 로그인, 꿀 충전·충전 취소·환급, 미션 후원과 익명 후원, 방송자 등급과 월 정산(송금은 목업), 신고와 방송자 활동 제한, 운영자 화면과 제재·이의 제기, 알림, 홈의 카테고리와 시청자 수, Docker, OpenAPI 문서.
- **만들지 않은 것:** 모바일 앱, 실제 광고, 채널 구독, 플랫폼 구독, 클립, 편성표, 라운지, e스포츠, 드롭스, 팔로우와 방송 시작 알림. 이유는 [07 기능 명세](07-feature-spec.md) 9장에 있다.

| 가치 | 심사에서 보여줄 수 있는가 |
|---|---|
| 설치 없이 바로 켠다 | 보여줄 수 있다 |
| 가입 없이 바로 본다 | 보여줄 수 있다 |
| 방송이 끝나면 후원 내역과 짧은 다시보기(녹화를 켰을 때)가 남는다 | 보여줄 수 있다 |
| 가볍게 켠 사람이 다시 켜서 입문 스트리머가 된다 | 기획서에서 설명만 한다 |
| 방송자가 다른 플랫폼보다 후원 수익을 더 많이 가져가고, 등급이 오르면 더 커진다 | 보여줄 수 있다. 후원 내역의 배분 비율, 내 등급 화면, 승급 뒤 바뀐 비율로 보여준다(06 결정 9) |
| 작은 방송이 모르는 시청자에게 발견된다 | 보여줄 수 없다. 위험으로 기록한다 |

## 8. 개발 전에 확인한 것과 결과

공모 요강으로 확인한 것이 세 가지다.

- 탭 소리만 보내도 소리 요구사항을 채운다.
- 휴대폰은 카메라와 마이크 송출만 하면 된다.
- 후원은 테스트 결제로 만든다.

개발 전(11월 5~8일)에 확인할 것으로 정한 다섯 가지와 그 결과는 다음과 같다.

| 순서 | 확인할 것 | 결과 |
|---|---|---|
| 1 | 심사 기기와 브라우저 | 요강에 적혀 있지 않았다. 맥북 크롬과 아이폰을 기준으로 정하고 README의 지원 환경에 적었다 |
| 2 | 맥북 크롬 탭 공유와 탭 소리 | 탭 공유와 "탭 오디오 공유"로 송출하도록 만들었다. 확인 방법은 README 기능 확인 순서 1번에 있다 |
| 3 | HTTPS 배포와 아이폰 카메라 | Vercel에 배포했다. 무료 한도는 공식 문서로 확인했다(06 "공식 문서 확인 결과") |
| 4 | 송출 구조와 다른 네트워크에서의 시청, 녹화 업로드 | LiveKit으로 정했다(06 결정 1). 녹화는 무료 한도 때문에 한 번에 3분, 월 50분으로 제한했다(06 결정 6, 27) |
| 5 | 2주 일정이 가능한지 | 11월 12일에 첫 개발을, 11월 14일에 배포를 마쳤다 |

일정이 모자랄 때를 대비해 [06 결정 기록](06-decisions.md)에 "일정이 모자랄 때 빼는 순서" 표를 만들었다. 결정 28에서 스펙을 줄이지 않기로 했고, 이 표에서 뺀 기능은 없다. 남은 위험은 심사 기간 내내 서버를 켜 둘 수 있는지다. 배포는 무료 플랜이라 한도를 넘으면 새 요청이 실패한다.

다섯 항목을 모두 정했다.

이후에 더 정한 것:

- Docker는 지금 만들지 않는다. 스캐폴딩할 때 서비스 주소와 키를 모두 환경 변수로 받게 해 두고, 필수 기능이 끝나 시간이 남으면 제출 전에 붙인다 (2026-11-07, 결정 10).
- 정산은 계산과 확정까지 실제로 만들고, 예약 작업과 송금은 목업으로 만든다. 목업은 외부 계약이나 실제 시간이 필요한 것만 대상으로 하고, 필수 기능이 끝난 뒤에 만든다. 일정이 모자라면 녹화보다 먼저 뺀다 (2026-11-07, 결정 11).
- 채팅은 영상용 LiveKit 연결로 실시간 전달하고 Firestore에 저장한다. 채팅 수정과 삭제는 만들지 않는다. 그래서 공모 요강의 선택 항목 "댓글 수정·삭제"와 "작성자 권한 검증"은 채우지 않는다 (2026-11-07, 결정 12).
- 운영자 화면(`/admin`, PC만)을 만든다. 신고(채팅, 방송, 사용자), 방송자 활동 제한, 운영자 제재(경고, 채팅 금지, 방송 금지, 영구 정지)와 이의 제기, 운영 기록을 함께 만든다. 심사용 "테스트 운영자로 로그인"을 두고 테스트 계정은 제재할 수 없게 막는다 (2026-11-07, 결정 13).
- 백엔드는 Next.js 서버 함수로 두고, 모노레포 안에서 서버 로직만 `packages/core`로 나눈다. 엔진엑스와 게이트웨이는 쓰지 않는다 (2026-11-07, 결정 14).
- PC 방송에서만 "내 얼굴도 같이 보여주기"로 화면과 카메라를 함께 보낼 수 있다. 화면만 하는 방송과 화면과 카메라를 함께 하는 방송을 모두 지원한다. 영상 두 개를 따로 보내고, 녹화는 둘을 한 영상으로 합쳐서 한다. 필수 기능이 끝난 뒤에 만든다 (2026-11-07, 결정 15).
- 프론트는 Next.js, TypeScript, Tailwind, shadcn/ui, zod와 React Hook Form, TanStack Query, Zustand로 만들고, 폴더는 FSD로 나눈다 (2026-11-07, 결정 16).
- 백엔드 서버 로직은 가벼운 헥사고날 구조(도메인, 유스케이스, 바깥 어댑터)로 나누고, 파사드는 두지 않는다 (2026-11-07, 결정 17).
- API 약속은 zod로 정해서 화면과 서버가 같이 쓰고, OpenAPI 문서는 그 약속에서 `zod-openapi`로 만든다. BFF 서버는 따로 두지 않고, 필요한 화면에만 화면 단위 읽기 API를 둔다 (2026-11-07, 결정 18).
- 준비 상태로 1시간이 지난 방송은 홈에서 숨긴다. 도배 제한용 문서를 더하고, 꿀 처리는 트랜잭션 하나로 묶고, 색인 목록을 처음부터 정한다 (2026-11-07, 결정 19).
- 헤더와 사이드바를 나눈다. 헤더 왼쪽에는 카테고리 대신 메뉴 링크(전체 방송, 다시보기)를 둔다. 오른쪽의 "스튜디오" 버튼이 예전 "방송하기" 버튼을 대신한다. 알림은 나비 안에서 일어난 일만 보여준다 (2026-11-07, 결정 20).
- 심사용 계정을 시드 스크립트로 만든다(처음 9개, 2026-11-14에 17개로 늘림). 시드는 실제 서버 기능을 거쳐 기록을 넣는다. 계정은 심사자가 함께 쓰고, 부분 초기화와 전체 초기화를 둔다. 홈의 방송 중 목록은 처음에는 채우지 않기로 했다가 예시 방송으로 채우기로 바꿨다 (2026-11-07, 2026-11-14 변경, 결정 21).
- 꿀은 나비가 파는 상품으로 본다. 쓰지 않은 꿀은 신청을 받아 10%를 떼고 본인 계좌로 돌려준다. 하루 충전 한도는 100만 꿀이고, 본인인증을 한 성인만 충전한다. 미션 후원은 대가가 아닌 응원이라고 약관에 적는다. 본인인증과 송금은 목업이다 (2026-11-07, 결정 22).
- 테스트 운영자는 시드 계정에만 조치할 수 있다. 실제로 가입한 사용자는 결정 25에서 조회도 막았다. 배포 주소에서 누구나 테스트 운영자로 들어올 수 있기 때문이다 (2026-11-07, 결정 23).
- 일정이 모자랄 때 빼는 순서를 06 결정 기록의 표 하나로 합쳤다 (2026-11-07).
- 방송 중에는 방송을 지울 수 없다. 내 방송 관리 목록에는 끝난 방송만 나오고, 준비·방송 중인 방송은 목록 위 카드로 보여준다. 녹화는 송출 화면에서 방송을 시작하기 직전에 고른다 (2026-11-07, 결정 24).
- 전수조사에서 나온 빈틈을 메웠다. 미션은 방송 중에만 받는다. 송출이 실제로 올라온 뒤에 방송 중으로 바꾼다. 꿀 내역 규칙을 표로 정했다. 충전 취소, 환급 승인, 정산 지급은 두 단계로 처리한다. 테스트 운영자는 시드 계정만 본다. 빼는 순서를 다시 정하고 날짜별 점검 지점을 두었다 (2026-11-07, 결정 25).
- 2차 전수조사에서 나온 빈틈을 메웠다. 환급할 꿀에서 묶인 꿀을 두 번 빼지 않는다. 외부 호출 결과를 모르면 조회로 정한다. 만드는 순서를 빼는 순서의 거꾸로로 정했다. 피그마 글 페이지는 "동작은 07이 기준"이라고 안내하고 매번 맞추지 않는다 (2026-11-07, 결정 26).
- 개발하면서 고치려던 47건을 개발 전에 모두 정했다. 시청 권한, 녹화 시간 제한, 저장 규칙과 색인, 채팅 필드, 신고 묶음, 정산 순번, 시드와 초기화 규칙, 공개 테스트 계정 제한이 들어간다 (2026-11-07, 결정 27).
- 스펙은 줄이지 않는다. 개발 중 송출 테스트는 LiveKit 개발 서버로 하고, 클라우드 LiveKit은 꼭 필요할 때만 쓴다. 토스는 사업자 없이 테스트 키로 연동한다. 실제 기기 테스트는 개발이 끝난 뒤 사용자가 한다. 3차 전수조사의 빈틈(초기화, 정산 보류, 운영자 가림, 탈퇴 조건 등)을 메웠다 (2026-11-07, 결정 28).
- 정책과 기획을 맞췄다. 방송자 약관을 기능에 맞추고 시청자 이용약관 초안([10](10-terms-of-service-draft.md))을 만들었다. 모든 충전 창에 동의 줄을 두고, 제재 중 탈퇴를 막고, 운영 조치를 알린다. 다시보기 약속은 "녹화를 켜면 짧은 다시보기가 남는다"로 바꿨다 (2026-11-07, 결정 29).
- 방송 중인 방송의 송출 화면에는 다시 들어갈 수 없다. 공용 테스트 계정에서 다른 심사자가 방송을 가로채지 못하게 하기 위해서다. LiveKit 방 이름은 방송 ID와 같다. 시작에 실패하면 연결을 끊고, 휴대폰에서 돌아오면 서버 상태로 화면을 고르고, 준비 상태 방송을 지우면 방도 닫는다 (2026-11-08, 결정 30).
- 홈을 콘텐츠로 채운다. 안내 카드, 대표 방송, "광고 예시" 배너, 카테고리별 방송 줄, 다시보기 줄을 둔다. 카테고리 8개와 시청자 수를 만든다. 시청자 수는 보여주기만 하고 정렬에는 쓰지 않는다 (2026-11-14, 결정 31).
- 광고는 개발하지 않고 운영 규칙만 기획으로 정한다. 입장 영상 광고와 홈 배너만 두고, 방송 중간 광고는 두지 않는다. 처음 들어온 시청자에게는 보여주지 않고, 같은 시청자에게는 30분에 1번, 하루 6번까지만 보여준다. 방송자는 자기 방송의 광고를 끌 수 있다. 출시 직후에는 입장 광고를 끄고 시청자가 늘면 켠다 (2026-11-19, 결정 32).

## 10. 판단 상태

- 기능은 모두 만들어 배포했다. 각 기능이 되는지는 [README](../README.md)의 "기능 확인 순서"로 확인한다.
- 막히는 지점 순위와 감정 점수는 레퍼런스 화면과 공식 문서로 한 추론이다. 실제 사용자로 확인하지 않았다.
